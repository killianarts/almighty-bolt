GUI Architectures, illustrated

One small data-entry screen, rebuilt several ways. Each architecture runs live below: edit the reading and watch which objects send which messages, then read the Common Lisp that would do the same job.

This page follows the structure and ideas of Martin Fowler's essay “GUI Architectures” (18 July 2006). The explanations here are a fresh retelling written for this page, not a copy of the original. The essay is worth reading in full; treat this as illustrations to keep open beside it.

The running example

A screen for ice-cream particulate

Abstract talk about “separating concerns” goes nowhere without a concrete screen, so the essay builds everything around one slightly absurd example. Across New England, monitoring stations sample the air for ice-cream particulate. Atmospheric modelling gives each station a target level. Someone keys in each actual reading, and the screen tells them how far it is from target.

That's a tiny screen, but it already has the three kinds of logic every GUI has to put somewhere. There's domain logic (variance is actual minus target), a domain judgement (a reading 10% or more under target is bad, 5% or more over is good), and view logic (bad shows red, good shows green). The architectures that follow differ mostly in where they put those three things, and in how the screen finds out that something changed.

Try it pick a station, type an actual
The variance rule

The marker is (actual − target) ÷ target. The boundaries are inclusive: exactly −10% is already bad, exactly +5% is already good.

The domain layer used by every version below. variance-category returns a judgement (:bad, :good, :normal), never a color. Rationals like -1/10 keep the boundary comparisons exact.

Architecture 1

Forms and Controls

Client-server tools of the 1990s: Visual Basic, Delphi, PowerBuilder

This is the architecture most people build without deciding to. You drag reusable controls (text fields, list boxes, grids) onto a form, and the form is a class you write. The form lays out its controls and holds any behavior specific to this screen. The name “Forms and Controls” is Fowler's label for this style; the tools of the time didn't call it anything.

The style is easiest to understand through the data. There are really three copies of the reading: the row in the shared database (record state), an in-memory record set the application loaded for this session (session state), and whatever the controls are currently showing (screen state). Much of GUI programming is keeping those three in step.

For plain fields, data binding does the work: the control is wired to a column of the record set and edits flow across without code. Binding copes badly with anything clever, though, and the variance field is clever. It has to be recomputed and recolored whenever the actual changes.

So the form registers for the control's events. When the actual field reports a change, a handler method on the form reads the fields it needs, does the arithmetic, and writes the variance and its color back into the variance control. Notice what that means: the subtraction, the 10%/5% thresholds and the color choice all live inside the form, tangled with widget calls. Later Fowler calls this way of keeping the screen current Flow Synchronization: the code that changes something is responsible for updating everything that depends on it.

text, background, bind-field and on-event stand in for whatever your toolkit provides (McCLIM, LTK, CAPI). The point is where the logic sits, not the toolkit.

Architecture 2

Model View Controller

Smalltalk-80, late 1970s to 1980

MVC is the most quoted pattern in UI design and probably the most misquoted. The name has been reused for so many different things that it now means little on its own, an effect Fowler elsewhere calls semantic diffusion. To get at the original, he ran an actual Smalltalk-80 implementation and looked at how it behaved. The essay treats MVC less as one pattern and more as two ideas that have outlived it.

The first idea is Separated Presentation. Domain objects should be complete without any user interface: you should be able to drive a reading from a script or a test, and put several different screens on it at once. The presentation layer may depend on the domain, but never the other way round.

The slider plays the controller. It only touches the reading. Both views are dependents of the reading and redraw themselves when it announces a change; neither knows the other exists.

The second idea is Observer Synchronization, which the demo above shows. Instead of a form pushing values into widgets, each view registers as an observer of the model. When the model changes, it broadcasts the change and every interested view refreshes itself. The code that changed the reading doesn't need to know who is watching.

Smalltalk-80 MVC also has no form object at all. Every widget on the screen is its own view and controller pair: the controller handles keyboard and mouse input and pushes the result into the model, and the view renders the model. A controller is configured with the name of the model's aspect it edits and calls that accessor reflectively. Views and controllers barely talk to each other; they meet through the model.

Where does the red go?

Variance is easy in MVC: it's arithmetic on a reading, so it belongs in the domain object, and the variance view just observes it. Color is the awkward part. Deciding that a reading is bad is a domain judgement, but deciding that bad means red is a presentation decision, and the standard text-field view has no idea how to make either. The essay walks through the options. Pick one to see it in code.

The specialized widget is the cleanest fit for classic MVC: the domain says :bad, the widget says red, and nobody crosses the line. The presentation model option is the seed of a bigger idea. Some state belongs to the screen rather than the domain (which station is selected, whether Save is enabled, what color a field is), and it needs a home that isn't a widget. That idea returns twice below.

Architecture 3

VisualWorks Application Model

ParcPlace VisualWorks, early 1990s

VisualWorks was a commercial Smalltalk that kept MVC's two big ideas but made two significant changes. It added a visual UI painter, and it put a new object between the widgets and the domain: the application model, a class written per screen that is close in spirit to the presentation model just mentioned.

The glue is the property object. Instead of a widget calling an accessor by name, it holds an object that represents a single value: you can read it, write it, and ask to be told when it changes. A value-holder keeps its own value, which suits presentation state such as the selected station. An aspect-adaptor wraps one property of some other object, such as a reading's actual, and passes reads and writes through. In the painter, you point each widget at an aspect of the application model and it gets an adaptor.

A property object, up close

Every widget speaks the same three-word protocol: read the value, write the value, tell me when it changes. That uniformity is what made the UI painter possible.

So edits flow from widget to adaptor to domain, and change notices flow back the same way. The variance field's adaptor observes the reading and refreshes the widget. That's still Observer Synchronization, now routed through the application model's property objects.

The color problem comes back, and it bites harder. An adaptor carries a value; nothing in the standard set carries “the color that goes with this value.” The usual way out was for the application model to grab the actual widget and set its color directly. It works, but it punches a hole through the layer that was supposed to keep widgets and logic apart. The essay presents that discomfort as one of the roots of MVP.

Architecture 4

Model View Presenter

Taligent / IBM in the mid 1990s (Potel, 1996); Dolphin Smalltalk (“Twisting the Triad”, 2000)

MVP takes something from each earlier style. From Forms and Controls it keeps the idea that the view is just a composition of ordinary platform widgets, with no per-widget controller. From MVC it keeps Separated Presentation and the model at the center. The new piece is the presenter: one object per screen that receives the user's gestures from the view and decides what they mean.

In Potel's version, the presenter turned gestures into command objects that changed the model, which makes undo straightforward, and the view stayed in sync by observing the model. Dolphin's version let the presenter also update the view directly when observation alone couldn't express the behavior. That's how MVP fixes the color problem without hacks: the presenter is allowed to talk to the view.

How much the presenter does is the real variable, and later writing split MVP into named variants. Switch between them below. Watch which arrows exist, not just the order they fire in.

Compared with MVC, the presenter works at the level of the whole screen, not a single widget. Compared with the application model, it's comfortable touching the view when it needs to, rather than treating that as an escape hatch. Compared with Forms and Controls, the model is the source of truth and the view only shows it.

Architecture 5

Humble View

Feathers, “The Humble Dialog Box” (2002); Meszaros' Humble Object

Once teams started relying on automated tests, the GUI became the part of the program nobody could test. Widgets need a running window system, are slow to drive, and break tests when the layout changes. Michael Feathers' answer was to make the dialog box humble: strip it down until it holds nothing worth testing, and move all the behavior into an ordinary object that tests can reach. Gerard Meszaros later generalized this as the Humble Object pattern.

All three MVP-era shapes can serve that goal, with different trade-offs:

Passive ViewThe humblest window: no bindings, no observers. The presenter writes every value and color. Test it by giving the presenter a fake view. The cost is writing and maintaining that test double.
Supervising ControllerSimple fields bind declaratively; the presenter handles only the tricky parts. Less code, but those bindings are only tested through the real UI. They are usually simple enough that this is an acceptable risk.
Presentation ModelAll view state and view logic live in a widget-free object (later popularized as MVVM). Tests talk to it directly, with no fake view. The leftover risk is the mapping from widgets to its properties, which is usually mechanical.

Architecture 6 · beyond the essay

    
Immediate mode

    
Named and popularized by Casey Muratori in a 2005 lecture; later Dear ImGui, egui and many game and tool UIs

  

  

    
Fowler's essay ends with Humble View, and every architecture in it shares one assumption: widgets are objects that live as long as the screen does. Each widget holds its own copy of what it displays, so each architecture is largely a strategy for keeping those copies current. That whole family is called retained mode.

    
Immediate mode drops the assumption. There are no widget objects. One function describes the entire screen, and it runs again every time the screen needs drawing. It reads the application's data directly, emits drawing commands, and reports what the user just did: (button ui :save "Save") draws a button and returns true on the frame it's clicked. Muratori argued for the approach as part of a broader critique of building programs as webs of objects that each guard their own state.

    
Because the screen is regenerated from the data each time, there's nothing to synchronize: no binding, no observers, no presenter pushing values into fields. The variance color is decided on the same line that draws the field. The domain still knows nothing about the UI, so Separated Presentation survives. The rest of the essay's machinery simply isn't needed.

And enabling or disabling becomes plain control flow: the Save button simply isn't drawn when there's no actual reading to save.

  

  






  

    
Immediate mode, continued · beyond the essay

    
Keeping the pixels: a cache behind immediate mode

    
Moritz Falk, “Don't throw it all away: Caching an immediate-mode UI”, Blick Blog, 21 October 2026; the UI Painter in the Blick video editor, described on its Metal backend

  

  

    
The usual answer to immediate mode's repeated work is the one in the demo above: run frames only when something happens. Falk's post about the Blick video editor argues that this stops being enough once battery life matters. A blinking caret, a moving playhead or an animated control keeps the app awake while almost everything else on screen stays the same, and high-resolution, high-refresh displays multiply the cost of every one of those frames.

    
His answer separates two jobs that immediate mode usually does together: “Reconstructing the UI and repainting its pixels are separate kinds of work.” The UI still rebuilds its whole description every frame. The renderer, which Blick calls the painter, keeps the pixels it produced last time and repaints only the parts whose drawing inputs changed. It works that out from the drawing commands alone, so the UI never has to track which widgets changed. A retained toolkit gets its dirty regions from widgets that know they changed; here they come out of the command stream, even though the UI was rebuilt from scratch.

  


  
A small rendering language

  

    
By the time a command reaches the painter, layout is done. The painter knows where shapes go, their colors, clips and textures, but not what a popup, a timeline or an audio clip is. On the Metal backend every command is a fixed 64 bytes, and the shader reads only the fields a given command needs. Some commands change how the ones after them are processed, so Falk describes the shader as a small interpreter that keeps a little state as it walks the list.

  

  

    
Analytic shapesRectangles, circles, lines, triangles, rings and diamonds. A distance function at each pixel gives edge coverage, fill and outline.

    
Textured shapesImages, glyph coverage and the results of other rendering passes, sampled and blended.

    
Shape groupsCombine several shapes' distance values, then give the result one fill and outline, so the edges inside an icon disappear.

    
Alpha barriersComposite a run of commands first, then apply one opacity, so a fading popup fades as a whole instead of showing its background through its text.

  


  
Which tiles need painting

  
  

    
The painter divides the window into a grid of tiles and works on them with ordinary compute shaders. A binning pass works out the area each command can affect and records, in bitsets, which coarse regions it overlaps. Each fine tile then checks its region's candidates and keeps the ones that overlap it. Every tile ends up with a short list of commands in the original drawing order; with alpha blending, swapping two shapes changes the result.

    
Two details are easy to miss. A command that begins a group draws nothing itself, but leaving it out of a tile's list would change what happens to the shapes after it, so group boundaries need bounds too. And a glow or shadow reaches past its shape, so its bounds must include that reach, or pixels that need painting get missed.

    
The same tile lists decide whether painting is needed at all. The GPU hashes each tile's commands in drawing order and compares the hash with last frame's. A match leaves that tile's pixels in the UI texture alone; a mismatch adds the tile to a work list. The GPU also produces the count that dispatches the paint pass, so the list never travels back to the CPU. In Falk's words: “We hash the command contents and their order. We are not comparing pixels to pixels.” In front of all this sits a cheaper check: if no commands or dependencies changed, no effects need rendering and nothing was explicitly invalidated, the painter doesn't run at all.

    
When a tile is painted, each pixel walks its list front to back. Once the pixel is fully opaque, the shapes behind it can't contribute and are skipped, unless a group or alpha barrier is still open.

The demo applies the same idea to the reading form, with Canvas 2D standing in for the GPU and painting back to front. One immediate-mode function emits about 30 commands per frame; the painter bins them into 20-pixel tiles, hashes each tile's list and repaints only the tiles whose hash changed. Hover a station and only the tiles under it flash. Leave the caret blinking and one or two tiles are repainted about twice a second. The extra frames after each input (immediate mode's settling frames) produce identical commands, so the first check skips the painter entirely. Switch to Repaint everything for the baseline Falk measured against.

    
Hashing commands instead of pixels has one trap: the hash has to cover everything the pixels depend on, not just geometry. Blick draws waveforms and video gradients in a separate effects pass into atlas textures, and the painter samples them like any other image. A rectangle can stay put while the picture inside it changes, so the effects code records content revisions and they go into the hash. The trend line here works the same way. Choose Ignore texture changes, press + a few times, and the line stops following the numbers above it. Choose Glow bounds too tight and click the Actual box: its focus glow is cut off at tile edges, because the tiles it reaches into never receive the command.

    
Both bugs show the testing idea in the post. Replay the same interactions with the cache on and off, capture images at matching points, and compare them: with the same inputs and animation times they must match exactly. Turn on Compare every painted frame and the demo does this after each frame, outlining tiles that hold stale pixels. Blick hasn't automated these checks yet, but having an uncached renderer as the reference is what makes them possible. The demo also had to handle one input that's easy to forget: when the web fonts finish loading, every glyph changes but no command does, so text commands carry a font revision in their hash, just as textures carry theirs.

  

  


  
What it saved, and what it costs

  

    
Falk measured a scripted light-editing session (pauses, playback, scrubbing, moving clips, editing titles) on an unplugged M3 Pro MacBook Pro at 60 Hz, once with the cache and once with full repainting forced. Both versions could sleep when nothing was happening; the only difference was whether they reused pixels when the app did update.

  

  

    
−20%CPU and GPU power, macOS estimate: 0.304 W cached against 0.380 W repainting

    
−14%whole-laptop power, from battery telemetry: 3.44 W against 3.99 W

    
−94%tiles painted over the same session

    
−87%GPU time spent in the painter

  

  
Two paired four-minute comparisons on 18 October 2026, both favoring the cache. The power estimates include other processes, the battery telemetry hasn't been independently validated, and the projected 2.4 extra hours of battery (about 17.4 h instead of 15.1 h, assuming 60 Wh usable) is an extrapolation, not a measured rundown. Falk calls it a small, synthetic test and plans heavier workloads and other hardware.

  

    
What the cache keeps

      
    
        
  • Immediate mode's programming model. The UI is still one function from data to commands, rebuilt every frame.
    • 
        
  • No dirty tracking in the UI. What to repaint comes out of the commands themselves.
    • 
        
  • Visual freedom. Groups and barriers build outlined icons and fading popups from simple commands, and their results are cached like anything else.
    • 
        
  • A reference to test against. The uncached painter defines what correct pixels look like.
    • 
      

    

    
What it costs

      
    
        
  • Work to find work. Binning and hashing take GPU time before any painting starts.
    • 
        
  • Little gain when much changes. Scrolling or animating large areas changes many tiles at once, and stacked translucent layers leave fewer pixels that can stop early.
    • 
        
  • Fixed capacity. Tile lists have a fixed size, which limits how many commands, group and barrier commands included, can overlap in one place. Only one alpha barrier can be open at a time, so fades can't nest.
    • 
        
  • The rest of the frame still runs. Rebuilding the UI, layout, command generation and presentation cost the same as before. Effects atlases need storage and tracking of their own.
    • 
      

    

  


  
Also in the post

  

    
Groups and glowsA shape group's combined geometry can also cast a glow, inner glow or shadow. Combined distance values aren't always exact signed distances, so smooth blends need care when outlined.

    
Barriers without texturesAn alpha barrier saves the pixel's result so far, starts a fresh one, then applies the opacity and combines the two, all in the pixel's local shader state, with no offscreen texture. The idea came from Anton Mikhailov.

The same choice on the web: HTMX and Datastar

  

    
Hypermedia libraries face the same decision from the server side. After the user saves a reading, the handler can send back the whole form, or just the fragments that changed: hx-swap-oob targets in HTMX, or signals and element patches in Datastar. HTMX's usual advice is to replace the whole form, because it's simpler; picking fragments can mean less rendering work, but it's more to get right.

    
The difference that matters is who decides what to update. Picking fragments by hand is retained-mode thinking: something has to know which parts of the page depend on which data, and one forgotten target leaves a stale total on screen, the “where does the red go?” problem moved to the server. Blick keeps the simple model, describe everything every time, and moves the selectivity into the layer below. The web has the same option: morphing. The server renders the whole form, and the client compares it with the live DOM and changes only the nodes that differ. Datastar's element patches morph by default, and HTMX does it with the idiomorph extension (hx-swap="morph").

The two worlds save different things. Blick's cache saves GPU painting, the expensive step in its frame. A browser already repaints only damaged regions, so replacing a whole form rarely costs much in pixels; the costs are server rendering, bytes on the wire, and above all the element state a replace throws away. Morphing keeps that state, much as immediate mode keeps focus and text buffers in a small store keyed by widget id.

  

  

    
Lessons that carry across

    
    
      
  1. Describe everything by default. Re-render the whole form or the whole frame, and let the layer below work out what actually changed. It's simpler, and it can't forget a fragment.
    2. 
      
  2. The layer below only saves work done after the description exists. Morphing doesn't save the queries, server rendering or bytes behind the full response, or the time spent comparing a large DOM; Blick's cache doesn't save rebuilding the UI, layout or command generation. When producing the full description is itself the expensive part, comparing it won't help.
    3. 
      
  3. Hand-pick for small values that change often. A progress figure or live count updating ten times a second shouldn't re-render a form each time. That's what Datastar signals are for, and it's the web's version of the blinking caret: the frame still runs, but the work it causes stays small.
    4. 
      
  4. Give the comparison stable identity. A morph needs element ids to keep the right state with the right row when a list is reordered, just as immediate mode needs stable widget ids. Missing ids are fixed by adding ids, not by picking fragments.
    5. 
      
  5. Tell the comparison what it can't see. Blick adds texture revisions because hashing commands can't detect new image contents. On the web, third-party widgets, web components and running animations hold state the morph can't see, so leave them out of the morph or update them explicitly.
    6. 
      
  6. Keep the full re-render as the test reference. Apply the same actions with fragments and with full re-renders, then compare the DOM or the values it shows. Any difference is a stale fragment, the web's stale tile.
    7. 
      
  7. Hand-picking is an optimization, not a design. Apply it where a measurement shows the full re-render is too slow, and nowhere else.
    8. 
    

  

  

    
For a native framework, the lesson is that choosing an immediate-mode API doesn't commit the renderer to repainting everything. Retained mode's best mitigation, repainting only what changed, can live entirely in the renderer, driven by the command stream, while the code that describes the UI stays as simple as before.

  






  

    
Costs, benefits and mitigations

    
What each paradigm buys, and what it charges

  

  

    
Neither family is free. Retained mode pays in synchronization: copies of state, notifications, and the objects that manage them. Immediate mode pays in repetition: it redoes work every frame, and it has to reconstruct things that a widget object would have simply remembered. Most costs on both sides have well-known mitigations, and many of those mitigations borrow from the other side.

  

  

    
Retained mode gives you

      
    
        
  • Idle screens cost nothing. Work happens only when something changes, and only the invalidated region repaints.
    • 
        
  • Widgets remember things. Focus, selection, scroll position, the text cursor and input-method state live in the widget.
    • 
        
  • The platform can see the UI. A persistent widget tree is what screen readers, UI automation, native look and system text services work from.
    • 
        
  • Layout is cached. Sizes are computed once and reused until something invalidates them.
    • 
        
  • Structure is data. Visual builders like the VisualWorks painter, and animations attached to objects, fit naturally.
    • 
      

    

    
Immediate mode gives you

      
    
        
  • No second copy of state. Nothing to keep in sync, so screens can't go stale.
    • 
        
  • Code that reads top to bottom. The UI's structure is the function's control flow: a hidden widget is an if, a list is a loop.
    • 
        
  • Little ceremony. No widget classes, adaptors, observers or listener teardown.
    • 
        
  • Dynamic UIs for free. Rows and panels that come and go need no create and destroy bookkeeping.
    • 
        
  • Headless testing. Feed scripted input to the frame function and inspect the draw list it produced.
    • 
      

    

  


  
Retained mode: costs and mitigations

  

    

      
Copies of state drift apartWidgets, session state and the database each hold a copy. Every code path that changes data has to remember every copy, and one forgotten path leaves a stale screen.

      
    
        
  • One source of truth. Widgets bind to the model and never cache values of their own.
    • 
        
  • Derive, don't store. Variance is computed from actual and target on demand, never saved as a third field that could disagree.
    • 
        
  • One-way data flow. All changes go through a single update function, and the view is re-derived afterwards (the Elm architecture, Redux).
    • 
      

    

    

      
Notification cascades and glitchesObservers fire on every individual change, in no particular order, sometimes in the middle of a multi-step update. A view can render a half-applied state, or redraw several times for one user action.

      
    
        
  • Batch changes into transactions. Queue notifications and send each distinct one once, after the last change. try it
    • 
        
  • Dataflow with dependency tracking. Signals, or Kenny Tilton's Cells library in Common Lisp, recompute dependents in dependency order, so no observer sees a partial update.
    • 
        
  • Trace notifications in development. A log like the message traces on this page turns “why did that redraw?” into a lookup.
    • 
      

    

    

      
Behavior is hard to followThe essay's own warning. Control flow is spread across observer registrations, so no single piece of code says “when the actual changes, recolor the variance.”

      
    
        
  • Wire each screen in one place. A presenter or builder that makes all the subscriptions is readable; subscriptions scattered across classes are not.
    • 
        
  • Prefer explicit updates where clarity matters. Passive View trades some decoupling for code that reads in order.
    • 
        
  • Tooling. Inspectors that show each object's dependents and the most recent notifications.
    • 
      

    

    

      
Leaks from forgotten listenersA model's list of dependents keeps closed windows alive, and those windows keep receiving updates. This is known as the lapsed listener problem.

      
    
        
  • Hold dependents weakly. Let the garbage collector drop views nobody else references (see the code below).
    • 
        
  • Tie subscriptions to widget lifetime. Destroying a widget removes its subscriptions; a with-subscription macro can guarantee it with unwind-protect.
    • 
      

    

    

      
BoilerplateAdaptors, view protocols, presenters and test doubles, repeated for every field on every screen.

      
    
        
  • Generate it from a spec. One Lisp macro can define the view protocol, the fake view used by tests, and the presenter skeleton together.
    • 
        
  • Let the metaobject protocol notify. A metaclass whose slot writes call changed removes all the hand-written :after methods.
    • 
        
  • Declarative binding tables. Describe the mapping from widget to aspect as data, like the VisualWorks painter did.
    • 
      

    

    

      
Dynamic structure is fiddlyWhen the list of readings grows or shrinks, something has to create, insert, reuse and destroy widget objects along with their subscriptions.

      
    
        
  • Keyed reconciliation. Describe the children you want on every update and let the framework diff them against the existing widgets by key. This is how React, SwiftUI and Compose put an immediate-style API over a retained tree.
    • 
        
  • Virtualize long lists. Recycle a screenful of row widgets instead of keeping one per record.
    • 
      

    

  


  

    
Glitches and redundant updates load a reading with and without batching

    
Loading a reading sets three slots in order: station, date, actual. Each setter announces its change straight away. The variance view redraws whenever it hears about variance, which depends on both the station's target and the actual.

    

    

    

  


  
Immediate mode: costs and mitigations

  

    

      
Redrawing when nothing changedA naive loop runs the frame function on every display refresh, 60 or more times a second, burning CPU and battery while the user reads.

      
    
        
  • Run frames only after input, plus a couple of extra frames so hover states settle. try it
    • 
        
  • Scheduled wakeups. A widget that animates asks for a frame at a specific time. The text caret in the demo asks for one every 530 ms to blink; egui calls this request_repaint_after.
    • 
        
  • Skip presenting identical frames. Hash the draw list and don't touch the GPU if it matches the last one.
    • 
        
  • Keep the pixels. Hash each screen tile's drawing commands and repaint only the tiles whose hash changed, as Blick's painter does. try it
    • 
        
  • Stop when no one can see the window. The demo pauses entirely when scrolled off screen.
    • 
      

    

    

      
Expensive work repeated every frameAnything written inside the frame function runs every frame, whether or not its inputs changed.

      
    
        
  • Memoize on a version number that the application increments when data changes. try it
    • 
        
  • Move heavy work out of the frame. Compute it when the data changes and let the frame only read the result.
    • 
        
  • Clip long lists. Call widget functions only for the rows that are visible; Dear ImGui ships a list clipper for this.
    • 
      

    

    

      
Layout needs sizes you haven't measuredWidgets are placed in a single pass, in call order. A container can't center or right-align content it hasn't drawn yet.

      
    
        
  • Use last frame's measurements and accept a frame of lag. It's invisible when the UI is redrawn anyway.
    • 
        
  • Discard and rerun. If measured sizes changed, throw the frame away and run it again before presenting (code below). egui does this for sizing passes.
    • 
        
  • A separate layout pass. Record lightweight element declarations, solve layout, then draw. The Clay layout library works this way.
    • 
      

    

    

      
Some state has to persist anywayFocus, text cursors, scroll offsets, expanded sections and animation progress can't be recomputed from the application data.

      
    
        
  • A small store keyed by widget ID. The table beside the demo shows all of it.
    • 
        
  • Stable, scoped IDs. Build IDs from names plus an ID stack pushed inside loops (with-id), so two “Delete” buttons in a list don't collide.
    • 
        
  • Collect unused state. Drop entries whose ID hasn't appeared for a few frames.
    • 
      

    

    

      
Accessibility, text input and native feelWith no persistent tree, screen readers have nothing to read, and input methods and platform text services expect native fields. The canvas above shows both problems.

      
    
        
  • Emit an accessibility tree from each frame. Build it from the frame's output and send only the differences to the platform; egui does this with the AccessKit library.
    • 
        
  • Delegate text editing. Place a native or hidden input element over the field while it has focus.
    • 
        
  • Choose the battles. For internal tools and in-game editors a non-native look is often acceptable; for consumer apps it rarely is.
    • 
      

    

  

  


  
The middle ground

  

    
Declarative frameworks such as React, SwiftUI, Jetpack Compose and Elm take immediate mode's programming model and keep a retained tree underneath. You write a function from state to UI and rerun it when state changes. The framework compares the new description with the existing widgets and updates only what differs, so the platform still sees persistent widgets. They pay with the cost of that comparison and have their own mitigations: memoized components, stable keys, and fine-grained signals that avoid rerunning whole functions.

    
For a native GUI framework, the choice is less either/or than it looks. Persistent widgets are what operating systems' accessibility and text services expect, and an immediate-style API is pleasant to write. Several designs sit in between: an immediate-mode API that builds a retained tree and reconciles it; retained widgets wired with dataflow cells instead of hand-written observers; or retained application screens with an immediate-mode layer for tools and debugging overlays.

  






  

    
Architecture 7 · beyond the essay

    
Principled reactive UI

    
Raph Levien, “Towards principled reactive UI”, September 2020; the Crochet prototype, built on the Druid toolkit for Rust

  

  

    
The middle ground at the end of the last section isn't one design; it's dozens. In “Towards principled reactive UI”, Raph Levien, then leading the Druid toolkit, surveys them in search of the best way to write reactive UI in Rust. He expects the answer to come from combining existing ideas rather than inventing a new one, and calls his method “mining, not stamp collecting”: the point isn't a catalog of frameworks but finding the richest seams in them. Every goal is treated as a trade-off, not a rule.

    
His frame for the whole field is a pipeline of trees. The architectures differ mostly in how each stage finds out what changed in the stage before it.

  


  

  
Six goals, each a trade-off

  

    
Concise app logicThe app should simply describe its current view, as in SwiftUI, Dear ImGui, React and Svelte. He finds the Elm-style Rust toolkits wordier, because every component needs extra plumbing to route its messages and state.

    
Actually incrementalSmall changes should cost little. Immediate mode repaints everything, which costs power. A virtual DOM rebuilds the whole description and diffs it, which he calls “half-incrementality”; it still slows as trees grow.

    
Proper tab focusMoving focus correctly needs support in the architecture. It rests on stable widget identity, which accessibility needs for the same reason.

    
Simple typesSwiftUI's statically typed view trees give confusing errors and slow compiles, and they resist scripting. Dear ImGui and Jetpack Compose avoid that complexity.

    
Simple control flowCallbacks, Druid's lenses and compiler transforms all add complexity that leaks into apps. Plain function calls are preferred.

    
Low overall complexityFull incremental-computation engines and SwiftUI's internal dependency graph are heavy. Makepad shows that a retained design can stay simple.

  


  
Finding what changed

  

    
Levien's answer to “actually incremental” starts with notifications. An observer gets a precise message (“this field changed, update yourself”), and handling it correctly takes a lot of context. He prefers notifications that carry almost nothing: “something in this area changed; recompute.” The app logic then runs again from the root, and any container that can tell its inputs are unchanged skips its whole subtree.

    
The old tree is never edited while the app runs. A cursor walks it in order, compares, and records a small mutation: skip these nodes, update that one. The mutation is handed to the widget tree afterwards, and a container whose part of the mutation is empty doesn't even pass it down. His inspiration was the Automerge library, where capturing precise mutations is essential for collaboration. For storing trees he prefers a flat sequence in preorder, as Jetpack Compose does, over DOM-style node objects, which are expensive per node.

Compare the two retained strategies on the same action: the mutation is identical, but the work it took to find it is not. Rebuilding and diffing runs and compares every node however small the change. Skipping unchanged subtrees runs only the path down to what changed, and when nothing changed it stops at the root. Immediate mode has no widget tree to update at all; it redraws everything, which is cheap per frame and costly in total.

  


  
Stable identity

  

    
If the view tree is rebuilt or rerun on every change, something has to connect each new description to the widget it describes. Widgets with internal state, like a text cursor, a splitter's position or an expanded row, need an identity that survives every rerun. Get it wrong and state lands on the wrong widget. Try it: expand a row, then insert a station at the top.

  

  

    
Whose state is this?

    

    

    

    

    
The expanded flag is widget state, not app data, so the framework stores it under the row's identity. Switching schemes resets the demo.

  

  

    
Levien compares five ways of getting identity:

  

  

    
Object identity (the DOM)The widget is a long-lived object and its identity is the object itself. This requires a retained tree that the app manipulates directly.

    
Call order (React's Rules of Hooks)State is matched to hook calls by the order they happen in, which is why hooks may not be called conditionally or in loops.

    
Explicit keys (Flutter)The programmer attaches a key where position isn't enough, typically to list items. The “by key” mode above.

    
Positional memoization (Jetpack Compose)A compiler plugin identifies each call by where it sits in the source and in the sequence of calls.

    
Call-site tracking (Moxie)Rust's #[track_caller] (stable since Rust 1.46) gives each call its source location with no compiler plugin. Crochet uses this too.

  

  

    
Crochet adds a twist borrowed from immediate mode: actions are delivered by position in the tree. A button reports its click as a return value, as in (when (button cx "Save") …), rather than through a registered callback. Levien describes Crochet as closest to Jetpack Compose. Among the differences: actions in the immediate-mode style instead of observables, no compiler plugin, and updates that always start from the root rather than recomposing only part of the tree.

  

  

  
Crochet is written in Rust; these listings retell its ideas in Common Lisp. column, label, station-row and the other widget calls stand in for a toolkit.


  
State tearing

  

    
Delivering actions as return values has a cost Levien spelled out later, in “Advice for the next dozen Rust GUIs” (July 2022). He calls it state tearing: “Because updates to app state (from processing events returned by calls to functions representing widgets) are interleaved with rendering, the rendering of any given frame may contain a mix of old and new state.”

    
The build runs top to bottom. When the + button reports its click halfway down, the labels above it have already read the old value and the labels below it read the new one. This is a different problem from misplaced identity above. A wrong identity stays wrong. A torn frame is repaired by the next build, if there is one.

How much this matters depends on the app. A game redraws 60 times a second, so a torn frame lasts 16 ms. Levien concedes that for apps “continuously updating at a high frame rate, an extra frame of latency may not be a serious issue, but I consider it a flaw.” An app that redraws only when something happens has no next frame coming: the torn screen stays until the mouse moves. His fix “basically involves running the app logic twice”, which is the Settle first policy. Deferring events avoids the mixed frame but presents a consistent stale one first, and still needs a second build.

    
Screen readers, tests and agents are less forgiving than eyes. An accessibility tree read just after the click describes whatever the last build produced. Publishing that tree only from a settled frame, one whose build changed no app state, keeps machines from ever seeing a torn one. The extra build is cheap when building is already designed to happen every frame.

How it turned out

  

    
Levien published the essay as a direction for research, not a finished design, and asked for criticism of the patterns that would be hard to express in Crochet. In a note added in May 2022 he judged the Crochet experiment “mostly negative”, citing a number of ergonomic and functional “paper cuts”, though several of its research goals were met. The “Advice” post names them: state tearing; optional widget modifiers, painful without named and optional parameters in Rust; keeping begin-container and end-container calls properly nested, which no compile-time scheme they tried fully enforced; and a mutable context threaded through the app logic, which adds noise and “effectively enforces the app logic running on a single thread.” His conclusion: “it would be possible to build UI with this architecture, but there were a number of pain points, so I don’t believe it would be a good experience overall.” Two of the four ease in Common Lisp: keyword arguments cover optional modifiers, and with- macros guarantee nesting. He points to the follow-up, Xilem, as a significant conceptual advance. The prototype's verdict doesn't diminish the essay: its goals, the pipeline of trees and its survey of identity schemes remain the most reusable parts.

  






  

    
Architecture 8 · beyond the essay

    
Xilem: synchronized trees

    
Raph Levien, “Xilem: an architecture for UI in Rust”, May 2022; prototyped in the idiopath branch of the Druid repository

  

  

    
“Xilem: an architecture for UI in Rust” is Levien's next attempt, written after Crochet. Its starting point is a problem specific to Rust: most UI architectures depend on shared mutable state, which Rust's ownership rules make awkward. He also revisits the field. Druid's lenses confused people; immediate mode is simple but struggles with complex layout and can render stale state (his Crochet experiment, a retained backend behind an immediate-mode API, was “not compelling”); the Elm architecture works but is verbose and handles components poorly; and React ports to Rust lean on interior mutability.

    
Xilem rests on four ideas: a view tree that is diffed against the previous one and applied to a retained widget tree; event dispatch along an id path, giving mutable access to app state at each step; Adapt nodes for composing components, replacing Druid's lenses; and an incremental engine specialized for UI, whose main tool is the Memoize node. He calls the result “conceptual, almost academic”: no real UI had been built on it yet.

  


  

  
Events travel down an id path

  

    
Xilem's most distinctive choice is how an action gets from a widget back to the app. Low-level events like hover and resize stay in the infrastructure; only semantic actions, like a click, reach the app. The action carries the id path of the widget that produced it: every id from the root down. Dispatch starts at the root, and each container uses its view state to find which child owns the next id. Along the way each node gets a mutable reference to app state, so the button's callback can simply change it. There's no observer, no setState, no message type to define. Then the app logic reruns, and rebuild diffs the new view tree against the old one.

    
Two node types shape that trip. An Adapt node hands its child a different slice of state: a reading component sees &mut reading, not the whole app. A Memoize node holds some data and a function that builds its subtree; on rebuild, if the data is unchanged, the subtree is skipped. With immutable data behind Rust's Arc, “unchanged” is a pointer comparison, not a deep one.
