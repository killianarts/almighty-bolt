#+TITLE: Core Scope
#+DATE: <2026-10-23 金> 
#+STATUS: PROPOSED

* Context
We are going to be running a series of experiments to create the best GUI
library in both Common Lisp and Coalton.

We are going to experiment making the following kinds of GUI libraries:

1. Retained mode
2. Immediate mode
3. Reactive hybrid ala Flutter/GPUI

These are different in a number of ways:

1. What the UI is. Long-lived widgets? A description rebuilt every frame? A
   persistent tree?
2. When build code runs.
3. How changes are found.
4. Persistent structure.
5. Identity.
6. Where savings come from.
7. Damage rectangles.
8. Possible kinds of bugs.
9. Code shape.
10. Accessibility/Machine Intelligence Friendliness.
11. Costs that grow.
12. Allocation.

Retained mode puts the most work on the developer, who has to keep the model and the widgets in sync. Immediate + cache puts the most on the framework, which rebuilds everything and removes duplicate work afterwards. The reactive hybrid sits between them: the developer describes the UI declaratively, and the framework tracks what is dirty.

The question is: how do these different modes effect code size, usability, and
speed/memory efficiency? And can a garbage-collected language like Lisp use
immediate mode or a reactive hybrid without suffering too much from code
complexity or memory use?

In any case, since we are exploring fundamentally different approaches to GUI
development, we need to decide what the /shared core/ functionality is and build
that first.

* Options
** Platform
SDL3 or native windowing per OS?
** GPU API
Native or WebGPU?
** Text
HarfBuzz and FreeType, OS text engine, or pure-Lisp shaper?
** Layout
Shared ala Flutter style constraint box layout, or per variant?
** Scope
All six shared-core areas from the charter now, or platform, GPU rendering,
text and layout now, with input primitives, replay and full instrumentation
added when needed?

* Evidence
Nothing has been measured yet. The decisions rest on prior art, vendor
documentation and the charter's priorities, and a superseding record can
revise them once the =null= baseline variant gives numbers.

** Prior art
- All three reference frameworks (Flutter, GPUI, RAD Debugger) draw their own widgets inside a native window,
  and none uses SDL or GLFW. See the prior-art table in the charter's
  "Platform layer" section.
- Windows GPU API: GPUI uses Direct3D 11 with HLSL shaders and DirectWrite for
  text. Zed first ran its Linux Vulkan path on Windows, then wrote a Direct3D 11
  backend after users reported that Zed "didn't run on their machines due to the
  Vulkan dependency". The post says "DirectX 11 is guaranteed to be available
  on Windows 7 or later, including Windows VMs", and reports a lower memory
  footprint. It also notes that Direct3D 11 required a third shader
  implementation (MSL, WGSL, HLSL).
  [[https://zed.dev/blog/windows-progress-report][Zed: Windows progress report]]
- The RAD Debugger uses Direct3D 11 (charter's prior-art table). I found no
  stated reasoning for it. I assume D3D 12's features were unnecessary and the
  extra memory needed for 12 naturally led Fleury to 11.
- Flutter's Windows backend is unclear: sources conflict between ANGLE over
  Direct3D 11 and Impeller on Vulkan. Not relied on.

** SDL3 and SDL_GPU (considered, not chosen)
- SDL3 would give windows, events, HiDPI scale, clipboard and timers on every
  OS with one C dependency, and basic IME through composition events and
  =SDL_SetTextInputArea= (since 3.2.0).
  [[https://www.mankier.com/3/SDL_SetTextInputArea][SDL_SetTextInputArea]]
- Rejected because the charter's reason stands: SDL hides the OS view that
  IME (=NSTextInputClient=, TSF) and accessibility (NSAccessibility, UI
  Automation) need, so serious work on either means reaching past it.
- =SDL_GPU= wraps Vulkan, Direct3D 12 and Metal, and =SDL_shadercross= converts
  HLSL or SPIR-V to the other formats. It presents to a window claimed with
  =SDL_ClaimWindowForGPUDevice=, which takes an SDL window; the documentation
  does not say whether a natively created window can be used. It offers
  Direct3D 12, not Direct3D 11, on Windows, and its limits are four color
  targets per render pass and four uniform slots per shader stage.
  [[https://wiki.libsdl.org/SDL3/CategoryGPU][SDL_GPU]],
  [[https://wiki.libsdl.org/SDL3/SDL_ClaimWindowForGPUDevice][SDL_ClaimWindowForGPUDevice]]
- Revisit if the Linux or Windows backends stall; the charter allows wrapping a
  portable library first if the variant contract does not change.

** Direct3D 12 requirements
Direct3D 12 needs Windows 10 or newer, Feature Level 11_0 and Resource Binding
Tier 2 or higher, a narrower set of machines than Direct3D 11. Its gains
(explicit memory, synchronization and multithreaded command recording) mainly
help CPU-bound draw-call-heavy renderers, which a batched 2D UI is not. This
is reasoning, not a measurement.
[[https://wiki.libsdl.org/SDL3/CategoryGPU][SDL_GPU backends and requirements]]

** Text
GPUI and the RAD Debugger use OS text engines (Core Text and DirectWrite;
FreeType on Linux for Fleury, a Rust stack for GPUI). Flutter bundles its own
stack. See the charter's "Text" section for the three options.

** Layout
- Flutter box constraints: constraints go down, sizes go up, the parent sets
  the position, in a single pass.
  [[https://api.flutter.dev/flutter/rendering/BoxConstraints-class.html][BoxConstraints]]
- RAD Debugger: size kinds (pixels, text content, percent of parent, children
  sum, each with a strictness) resolved in five passes per axis at the end of
  the build.
  [[https://raw.githubusercontent.com/EpicGamesExt/raddebugger/master/src/ui/ui_core.h][ui_core.h]],
  [[https://raw.githubusercontent.com/EpicGamesExt/raddebugger/master/src/ui/ui_core.c][ui_core.c]]
- Hypothesis H6 and the layout spike in the charter test whether the immediate
  mode branch needs the box tree.

* Decision
** Platform: Native
** GPU API: Native, per OS
- macOS: Metal (first target)
- Windows: Direct3D 11, with HLSL shaders. Chosen over Direct3D 12 and
  Vulkan for wide hardware and driver support, and for less code to
  maintain in a 2D renderer. GPUI and the RAD Debugger both use it.
- Linux: Vulkan, decided when we get there.
** Text: OS text engine
** Layout
Start with Flutter style constraints. Consider testing a RAD Debugger immediate
mode box tree model for the immediate + cache mode branch.
** Scope
In the core now: platform, GPU rendering, text and layout.

Kept from the start, because they are cheap now and expensive to add later:
- Input: plain event structs with timestamps, as the platform layer's output.
- Clock: one monotonic core clock. All time goes through it, so replay can
  substitute a virtual clock later.
- Instrumentation: a preallocated per-frame ring buffer holding the clock and
  =sb-ext:get-bytes-consed=.

Added later, each when its trigger is reached:
- Input primitives (stable ids, hit testing, focus): when the first
  interactive variant needs them (7GUIs Counter).
- Replay (script format, checkpoints, recording, test-id targeting): when the
  first variant renders.
- Full instrumentation (phase breakdown, trace output, settle statistics,
  build-time switch): before the Phase 3 benchmarks.

Not in the core for now: software rendering (a CPU rasterizer for tests or as a
fallback). Revisit if CI without a GPU, or users without a usable GPU, become a
problem.

* Consequences
** Platform
First macOS (AppKit), then Windows (Win32), then Linux (Wayland and X11,
decided when we get there).
- Easier:
  - Direct access to the OS view (=NSView=, =HWND=), which IME
    (=NSTextInputClient=, TSF) and accessibility (NSAccessibility, UI
    Automation) both need.
  - No extra C dependency, and the smallest image.
  - We own the event loop, so "frames only on request" and "idle means asleep"
    need no workaround.
- Harder:
  - Each OS gets its own window, event loop, timers and clipboard, and key,
    HiDPI and focus quirks that a portable library would have absorbed.
  - AppKit is reached through the Objective-C runtime and Win32 through CFFI.
  - macOS requires the event loop on the main thread, so the REPL cannot be
    the UI thread. The UI thread owns the loop and the REPL queues work to it.
  - Access to the OS view is not the same as having IME and accessibility. The
    bridges are still ours to write (Phase 6).
  - Window code can only be tested on an OS that has a backend. Tests that need
    no window (layout, display-list contents) run anywhere.
- Gives up: the quick start of SDL3. The charter still allows it as a stopgap
  if a platform stalls, as long as the variant contract does not change, which
  is also why adding an OS does not affect the variants.
** GPU API
- Easier: wide hardware and driver support, and no resource-state or fence management.
- Harder:
  - Metal Shading Language and HLSL are two shader languages, with a third (Vulkan's) later on Linux.
  - Direct3D is COM, so CFFI needs hand-written vtable wrappers.
  - Three renderers have to look identical. With no software renderer to act as the reference, plan golden screenshots read back from each GPU backend and compared with a tolerance, plus display-list tests that need no GPU.
- Gives up: Direct3D 12 and Vulkan features that a 2D UI is unlikely to need, and a shared Windows/Linux renderer.

** Text Engine
OS text engine makes text look like the user expects in their OS, least work.
Linux will be harder, so we'll figure it out later.
- Easier:
  - The smallest image, with no HarfBuzz or ICU to bundle.
  - Correct shaping for every script the OS supports, system fonts, font
    fallback and emoji.
  - Text that matches the user's other applications.
- Harder:
  - Core Text and DirectWrite sit behind one measurement API: measure a run,
    break a paragraph to a width, map a point to a caret, map a caret to a
    rectangle. The shared text cache is therefore per OS.
  - Metrics, shaping details and antialiasing differ by OS. The bundled test
    font set matters more, and every result record names its OS.
  - Frame hashes and screenshots are comparable only on one OS, not across
    them.
  - Linux has no single OS text engine. The charter's fallback is a bundled
    stack (HarfBuzz and FreeType through CFFI), which brings the C dependency
    and image size back on that platform. Whether tests use that stack on every
    OS, to make results comparable across machines, is left open.
- Gives up: identical text on every OS. This sits against the Beauty
  priority's "same look everywhere", so it is a deliberate exception for text.

** Layout
Flutter style works well in multiple styles and potentially makes end-user API
easier to understand and use, but the immediate + cached mode may reap extra
benefits from box tree.

** Scope
- Easier: a smaller Phase 1, so a window and a rendered display list arrive
  sooner. The triggers above pre-approve the later additions, so each needs no
  separate request to change the core.
- Harder: the seams have to hold. No code calls the system clock directly, and
  events stay plain serializable data. Otherwise adding replay later means
  hunting down every time call and redesigning the event types.
- Gives up: Phase 1 as the charter wrote it, which included instrumentation and
  input replay. Benchmark numbers are not trustworthy until full
  instrumentation exists, and replay-based tests and golden frames start only
  after the first variant renders.
- Also gives up: a CPU renderer, and with it GPU-less CI and a fallback for
  users without a usable GPU. Replay checks hash the display list instead of
  the pixels, which covers everything above the renderer.
