Principles of fast software, 2: what to do

Five strategies that follow from the first five principles, and two about organising a project so the strategies can be applied now and changed later.

Before you start

These seven follow from the five on Principles 1, but each stands alone. The example throughout is a small GUI core that must produce a finished picture, a frame, every 16.7 milliseconds. To allocate is to ask the language runtime for fresh memory, which a garbage collector later frees, pausing the program while it works. The notes headed Elsewhere describe well-known practice in other fields. They are not measurements from this project, and the glossary covers any other word you need.

The ideas, continued

Strategies and practice

The first five principles say what to optimise for and what machines are like. These seven say what to do about it: five strategies (P6 to P10), then two about organising a project (P11 and P12). As before, each has four notes: why it is true, how the core shows it, what it costs and where it stops applying, and where else it appears.

Principle 6 · strategies that follow

Pay once, use many times

A cost matters in proportion to how often it is paid. Move expensive work to where it happens once, and reuse the result.

Why it is true

Total cost is price multiplied by count. A frame loop runs 60 or 120 times a second for hours, so anything inside it is multiplied enormously, while the same work at startup is paid once. Much of performance work is finding what is multiplied (the hot path) and moving work out of it to somewhere it happens once (the cold path).

The idea takes four forms with one logic. Precompute: compile the shaders at startup. Preallocate: make the storage once. Cache: keep the result of an expensive call. Resolve early: look a name up once and keep the answer. The core's first rule is the second form applied to memory.

The question "how often?" also covers exceptions. Make the common case cheap and the rare case correct. Each text line records, when it is made, whether its string has any character that UTF-16 writes as two units. Only then are indices converted. Ordinary text, which is nearly all text, pays nothing.

In the core
  • The display list's arrays, the instance buffer and the frame ring are made up front (Part 1, Part 3, Part 4).
  • Apple's classes and message names (selectors) are looked up with load-time-value, which computes a value once, when the code loads, so the compiled call holds an integer and never searches by name. ensure-class builds each Objective-C class once (Part 2).
  • The shaders are compiled at startup, which takes 46 to 50 ms cold and about 1.4 ms with the system cache warm, and the pipeline is kept (Part 4).
  • get-line keeps each shaped line. Each glyph is rasterized once into the atlas (Part 5).
Cost and limits
  • Memory held in reserve. At the default capacity of 65,536 commands the display list takes about 1.6 MB and the instance buffer about 2.1 MB (25 and 32 bytes a command), whether a frame draws ten commands or sixty thousand. This is why the principle is not "memory efficiency". It spends memory to buy predictable time.
  • Stale results. A cache is right only while the world it copied stays the same. The line cache is safe because a font and a string are values that do not change, and it stores its own copy of the string it is keyed on (P10). It has no eviction, so it grows with every distinct string.
  • Where you pay matters. "Once" is not the same as "before the frame". The core pays lazily. The first frame that shows a new string shapes it, and the first frame that needs a new glyph rasterizes it, inside that frame. The charter allows for it by saying the zero-allocation rule holds "after warm-up". A stricter design would fill the caches at load time or while idle, and the core does not yet.
  • It needs repetition. Work that happens once anyway gains nothing from being moved.
Elsewhere
  • Servers. Connection pools, prepared statements and compiled templates move set-up cost out of each request.
  • The web. HTTP caching lets a server say that a response may be reused for a stated time.
  • Language runtimes. Just-in-time compilers compile hot code once and reuse it. Memoising a pure function caches its answers.

Principle 7 · strategies that follow

Do nothing when nothing changes

The cheapest work is the work you skip. Spend effort in proportion to what changed, not to how big the thing is.

Why it is true

A window that looks the same needs no new frame. A program that wakes sixty times a second to redraw an identical picture uses power, warms the machine and competes with everything else, for no visible result. Waiting is nearly free for an operating system, because a sleeping process uses no processor time. Polling, asking again and again whether anything changed, is not free. So let the thing that knows about the change wake you: the operating system, an event, a message.

The same idea at a smaller scale says that work should grow with the size of the change, not with the size of the whole.

In the core
  • The view is paused and draws only when request-draw marks it as needing a frame. Otherwise AppKit's run loop (the operating system's loop that waits for events) sleeps (Part 3). The charter states it as a rule: "Idle means asleep. The core blocks in the OS when nothing is pending. It never polls, never spins, and never presents a frame nobody asked for."
  • Input arrives as events and is never polled for.
  • Measured: a still window drew nothing, and an idle window used about 1 ms of CPU in 10 seconds and allocated nothing.
  • Immediate mode (Part 1) rebuilds the whole picture every time a frame is drawn. That would be wasteful if frames were continuous. Combined with drawing only on request, the rebuild happens only when something changed.
Cost and limits
  • Someone must know that something changed. If a change is missed the picture goes stale, and the bug looks like nothing happening, which is hard to find.
  • The core does not finish the job. When a frame is drawn the whole window is redrawn. Redrawing only the changed region, a damage rectangle, is on the not-finished list. And after sustained drawing an idle window sometimes shows a few wakeups (0, 7 or 26 in 10 seconds) whose cause is unknown. The principle is easy to state and hard to satisfy completely.
  • A game or an animation changes every frame, and the principle does not apply.
Elsewhere
  • HTTP. A 304 response means nothing changed, so reuse what you have.
  • Web interfaces. HTMX and Datastar replace one fragment of a page instead of reloading all of it. React-style libraries compare the old and new description of the interface and touch only the differences.
  • Build tools. Incremental builds, such as make, rebuild only what depends on a changed file.

Principle 8 · strategies that follow

Cross boundaries rarely, in bulk

Every crossing between systems has a fixed cost. Cross less often, and carry more each time.

Why it is true

A call across a boundary costs something before any useful work starts. The boundary may be from Lisp into Apple's code, from the CPU to the GPU, from one thread to another, or from one machine to another. Arguments are arranged, context is switched, an answer is waited for. For N crossings the cost is N times the fixed price plus the useful work, and batching pays the fixed price once. This is P6 applied to the fixed part of every call.

It is a separate idea from P5. Uniform work is what makes a batch possible. This principle says why a batch is wanted.

In the core
  • One draw call (one command to the GPU) for the whole frame: the same four-vertex strip drawn N times with instanceCount: N, instead of one call per rectangle. In the devlog, encoding and committing a frame took about 10 µs for anything from 10 to 1,000 commands, and 47 µs at 10,000 (Part 4).
  • One copy of the display list per frame into one buffer, and one 16-byte write for the frame constants.
  • One texture holds every glyph, so a frame binds it once (Part 5).
  • The crossings that cannot be avoided are made cheap. Each Lisp call into Apple's code compiles to a direct objc_msgSend with a fixed signature and a constant selector. A full round trip into Apple's code and back into a Lisp callback measured 23 to 28 ns (Part 2).
Cost and limits

Batching needs items that can be grouped. It adds delay, because you wait to collect the batch. It needs a limit on batch size (P9). And it moves complexity into the code that gathers the batch.

Elsewhere
  • Databases. The N+1 query problem: fetching a list of rows and then running one query for each row, instead of one query for all of them. It is probably the most common avoidable cost in web applications.
  • Operating systems. A system call costs far more than an ordinary function call, so programs read and write files through buffers instead of a byte at a time.
  • Networks. Many small requests each pay the round-trip delay. Batch APIs, bulk inserts and larger packets all carry more per trip.

Principle 9 · strategies that follow

Bound everything

Give every queue, buffer and cache a size you can state, and decide in advance what happens when it fills.

Why it is true

Anything without a limit will eventually be too big, and it will happen at the worst moment, under load, when memory and time are already scarce. Growth is also an allocation (P1). A bound turns an unpredictable failure into a predictable one, and into a number a test can check.

When a bounded thing fills there are three honest answers. Fail loudly, so that the problem is seen where it is caused. Drop the oldest, when only recent history matters. Make the producer wait, which is called backpressure. The choice has to be made on purpose. An unbounded queue only postpones it until the machine runs out of memory.

Cost and limits

You have to choose the numbers. Too small fails in front of a user, and failing loudly in the middle of a frame is harsh for a GUI, which the core accepts for now. Too large wastes the memory held in reserve (P6). And a bound is only as good as the answer chosen for the full case: an error is right for a display list and wrong for a log, where overwriting the oldest is right.

Elsewhere
  • Servers. Web servers cap request sizes and connection pools. Pagination returns a page of rows instead of all of them.
  • Caches. An unbounded in-memory cache is the classic memory leak.
  • Networks and logs. TCP's receive window is backpressure: a slow receiver tells the sender to wait. Linux's kernel log is a ring that drops its oldest lines.

Principle 10 · strategies that follow

Reuse needs an owner

Whenever storage is reused, someone must be able to say who may touch it now and when it is free again.

Why it is true

A garbage collector answers "when is this memory free?" for you: when nothing refers to it. When you reuse storage yourself (P6) you take that question back. If two parties use the same storage at the same time, one sees the other's half-written data. Such bugs depend on timing, so they are rare, they vanish when you look, and they are hard to find.

There are two clean answers to "who may change this?". One is nobody: an immutable value can be shared freely because nothing can change it. The other is one party at a time, made explicit by a hand-over, a wait, a lock or confinement to a single thread.

In the core
  • A reused buffer forces a wait. The GPU reads the instance buffer while the CPU would like to write the next frame into it, so each frame first waits for the previous one to finish. That wait is the price of reusing one buffer. Overlapping frames would need several buffers and a signal for when each is free again. Part 4 explains the options, and one of them is untried.
  • Confinement. AppKit may only be touched from the main thread (a thread is one line of execution in a program, and a program can run several at once on shared memory). Other threads do not touch it. They hand a function to the main queue (Part 3).
  • Reference counts. Each of Apple's objects keeps a tally of its owners, a reference count, and is freed when the tally reaches zero. The runtime keeps the tally where the Lisp collector cannot see it. So the core retains and releases them, uses autorelease pools, and keeps the previous command buffer alive until the next frame has waited on it. A Lisp struct that Objective-C names by index stays reachable because a table holds it (Part 2).
  • Valid until cleared. A command's index in the display list means something only until the list is cleared for the next frame (Part 1).
  • Immutable values. Events are immutable structs. The shaped lines in the cache are made once and not changed afterwards, and the cache copies the string it is keyed on, so a caller who later changes the original cannot corrupt it (Part 5).
Cost and limits

Waiting has a cost. When a frame is heavy the CPU stalls until the GPU is done. More buffers remove the wait but add memory, add a frame of delay between an input and its picture, and need the signal. Counts, locks and hand-overs are manual discipline, and mistakes show up as crashes or corrupt pictures rather than clean errors. Immutable values avoid the problem but allocate each time something changes, which is why the core reuses buffers inside the frame and uses immutable values outside it.

Elsewhere
  • Languages. Rust's ownership rules and C++'s RAII settle the question at compile time. Go's advice is to share memory by communicating, so that one goroutine owns each piece of data at a time.
  • Databases and the web. Two requests that update the same row race each other. Transactions, locks and version columns are the ways to say who may write.
  • Operating systems. Virtual memory gives each process its own address space, so no other process can touch its memory.

Principle 11 · how to build it

Keep a narrow boundary of plain data

Put a small interface made of plain data between the parts, so that each part can be tested, replaced and measured alone.

Why it is true

An interface that carries values, such as a list of numbers, can be inspected, compared, stored, replayed and produced by anything. An interface that carries behaviour, such as objects with methods or callbacks into shared state, can only be exercised by running the whole thing. A narrow data boundary lets you test one side without the other, swap either side, and time each on its own.

Treating time and input as ordinary values on that boundary, instead of reading them from the world, makes a run repeatable (P2). A related rule is to supply mechanisms and leave policy to the caller.

In the core
  • The display list sits between whatever decides what to draw and the renderer. The first only writes to it and the second only reads it (Part 1). The charter makes this a rule: a variant talks to the core only through a written contract. A variant is one candidate GUI library, and the project's experiment is to build several on this one core and compare them.
  • The charter also says the core provides mechanisms (draw this, measure that) and never decides what to draw or when state changes. Those decisions are the experiment.
  • A test can build a list and hash it or compare it with no window and no GPU. A baseline variant that only replays a fixed list would measure the core's own cost. It is on the not-yet-built list.
  • Events are immutable structs that print and read back, so a session can be recorded and replayed. Time comes from now-ns, which a test can replace (Part 3). The renderer can draw into an off-screen texture with no window (Part 4).
Cost and limits

A boundary must be general enough for every client, so it grows slowly. The display list has no borders, shadows, clips or transforms yet. Data that crosses it is copied or shared, with the costs in P4. And behaviour that does not fit a description, such as a trick that depends on the renderer's internals, cannot cross.

Elsewhere
  • The web. A server that sends HTML sends a description and lets the browser decide how to draw it. An HTTP API is a boundary made of data.
  • Interface libraries. React and Elm describe the interface as a function of state, and that description is the data that crosses the boundary.
  • Unix. Programs joined by pipes exchange plain text streams, so any program that reads and writes text can be swapped in.

Principle 12 · how to build it

Start simple, and list what you skipped

Build the simplest thing that meets the measured need. Put seams where you expect to change your mind, and write down what you left out.

Why it is true

You cannot know in advance which part will be slow, and guesses are often wrong (P2). Complexity added early is paid for in every later change, whether or not it helped. But the simplest thing must not be a dead end. A seam is a narrow place where one piece can be replaced (P11). Put seams where you expect to be wrong, and improve one piece when a measurement says to.

The last half of the principle is the list. A simple version has limits, and a limit that nobody wrote down becomes a surprise later.

In the core
  • The simple choices are each recorded: one frame in flight, a line cache and glyph atlas without eviction, glyphs snapped to whole pixels, a full redraw instead of a damage rectangle, and shaders compiled at run time instead of offline with a toolchain that would need full Xcode (Part 4, Part 5 and the not-finished list).
  • The project keeps a devlog entry for each experiment and a decision record for each design question that an experiment settled. Limits that were left in are listed, as in the not-finished list that closes the tour.
  • Seams were placed first: the clock, the ring, the event structs and the display list were built before the window.
Cost and limits

Someone has to remember the limits, which is why they are listed. Some seams are guesses and end up in the wrong place. And "simple first" has limits of its own: some decisions, such as how data is laid out (P4), are expensive to change later, so they deserve thought early.

Elsewhere
  • Rules of thumb. "Make it work, make it right, make it fast." Knuth's warning about premature optimisation has a second half: do not pass up the critical few per cent.
  • Databases. Migrations that add a new column before removing the old one keep every step reversible and every version working.
  • Engineering practice. Architecture decision records and changelogs are lists of what was chosen and what was skipped.
