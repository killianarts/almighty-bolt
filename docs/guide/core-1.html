What a GUI core does

A screen is a grid of coloured dots called pixels. Most screens redraw the whole grid 60 times a second, and some do it 120 times. Each redraw is a frame. To show a moving or changing interface, a program has to hand the computer a finished picture for every frame it wants shown.

The operating system does not draw your window for you. It tells your program when something happens: a mouse click, a key press, a resized window. These notifications are events. Your program answers by deciding what the window should look like and producing pixels for it.

The core in this project is the layer that does that plumbing so the interface code above it does not have to. It receives events, lets the interface code describe a picture, and turns that description into pixels using the graphics chip, the GPU. It is written in Common Lisp and runs on macOS, using Apple's Metal for graphics.

At 60 frames a second there are 16.7 milliseconds for everything between an event and the finished picture. At 120 there are 8.3. The core has to stay far inside that.

Three rules the core follows, and the ideas behind them

Three rules appear throughout the code. Each is a consequence of a deeper principle. The two Principles pages name them, and the small badges below, such as P1, link there.

1. A frame allocates nothing. To allocate is to ask the language runtime for a fresh piece of memory. Lisp has a garbage collector that later finds memory nobody uses and frees it. While it works, the program may have to stop. If that stop lands in the middle of a frame, the frame is late and the user sees a stutter. The core avoids the problem by not creating garbage while drawing: it makes its storage once and reuses it. The rule follows from judging by the worst case (P1). Making storage once is one form of paying a cost once (P6), and its price is memory held in reserve, so it trades memory for predictable time. It does not save memory.

2. Things are addressed by integers. Computer memory is a very long row of numbered boxes. A box's number is its address, and a pointer is a value that holds an address. Apple's objects, classes and method names are all reached through such addresses. Rather than wrapping each address in a Lisp object, the core keeps it as a plain 64-bit integer. Integers of that size are cheap to pass and create no garbage. This is bits and conventions (P3).

3. Draw only when asked. A game redraws constantly. An interface does not need to: if nothing changed, the picture is already right. So the core draws a frame when something requests one, and otherwise the whole process sleeps. A measured idle window used about 1 ms of CPU in 10 seconds and allocated nothing. This is doing nothing when nothing changes (P7).

Why a GUI core is a good teacher

A GUI core meets almost every pressure that shapes fast software, all in one small program. It has a hard deadline that anyone can see being missed. It is written in a language with a garbage collector. It calls a foreign runtime, Apple's, which has its own rules for memory. It drives a GPU, depends on a text engine, and answers a human who acts at unpredictable moments.

Each pressure forces a decision, and the decisions fall into a small number of patterns. The Principles pages name those patterns as twelve principles. The five parts of the tour, three on this page and two on the next, show them in working code.

Where the other small files fit

Three small, portable files support all of this and do not depend on macOS: clock (one function that returns the time in nanoseconds), ring (a ring that holds a preallocated log of how long each frame took) and event (the event structs). They are covered inside Part 3.

Part 1 of 5 · src/display-list.lisp

The display list

Principles at work

P6 The arrays are made once. P9 The list has a capacity and fails loudly when it is full. P4 One array per field. P3 A colour is one packed word. P11 The list is the narrow boundary between whatever draws and the renderer. P2 A frame can be hashed and compared.

The display list is the handover point between the code that decides what the window shows and the code that draws it. It is a flat to-do list for the renderer: "draw a blue rectangle here, a rounded rectangle there, this letter over there." The renderer reads it, and nothing else about the interface matters to it.

Describe everything, every frame

There are two ways to build an interface. In a retained design the program keeps a tree of long-lived objects (buttons, labels) and changes them over time. In an immediate design the program describes the whole picture again on every frame, from its current state. The core takes the immediate approach. It is simpler to reason about, because the picture is always a direct function of the state, and it makes tests easy: build a list, compare it.

The cost is that the list is rebuilt every frame, so building it has to be nearly free. That drives every choice below.

What one command holds

Every command is a rectangle with a colour, plus one number whose meaning depends on the kind of command.

FieldMeaning
kind0 rectangle, 1 rounded rectangle, 2 glyph (one letter)
x, y, width, heightWhere it goes, in points measured from the window's top left. Y grows downward.
parameterThe corner radius for a rounded rectangle, or the glyph's slot number in the glyph atlas for a letter (Part 5).
colorRed, green, blue and alpha (opacity), packed into one 32-bit integer.
Points and pixels

A point is a logical unit that stays the same size across screens. On a Retina display one point is 2 by 2 physical pixels, so the scale is 2. Layout is done in points and the renderer multiplies by the scale at the end.

Parallel arrays instead of a list of objects

The obvious design is a vector of command objects. The core stores each field in its own array instead, which is called a struct of arrays. The two layouts hold the same data.

Concept: the heap, boxed and immediate values

When a program allocates, the runtime hands out a piece of its pool of memory, called the heap. A value kept on its own piece of heap is boxed: it has a small header, and everything else refers to it by pointer. A value small enough to sit directly in a machine word, the 64 bits the CPU handles at once, is immediate and needs no heap piece. In SBCL, small integers (called fixnums) and single-floats (32-bit numbers with a fractional part) are immediate. Double-floats (the 64-bit kind) are usually boxed.

Make it once, reuse it forever

make-display-list allocates every array up front, sized for a capacity (65,536 commands by default). Clearing the list for the next frame only resets a counter. Adding a command writes into the slot at the counter and bumps it.

display-list.lisp, the heart of push-command

(let ((i (display-list-count display-list)))
  (when (>= i (display-list-capacity display-list))
    (error 'display-list-full :capacity (display-list-capacity display-list)))
  (setf (aref (display-list-xs display-list) i) (float x 1f0)
        (aref (display-list-ys display-list) i) (float y 1f0)
        ;; ... width, height, parameter, colour, kind ...
        (display-list-count display-list) (1+ i))
  i)

If a frame emits more commands than the list was made for, it signals an error. That is deliberate: growing the list mid-frame would allocate. Making the arrays once is P6 and the fixed capacity is P9. The price is memory held in reserve: at the default capacity the arrays take about 1.6 MB (25 bytes a command times 65,536) whether a frame draws ten commands or sixty thousand.

One colour, one integer

Hashing a frame so tests need no GPU

display-list-hash runs every field of every command through a hash function (FNV-1a) and returns one number. Two frames that draw the same things give the same number. A test or a replay can therefore check "did this produce the same frame as last time?" without a window or a GPU.

The result is trimmed to 62 bits on purpose. A Lisp fixnum holds 62 bits as an immediate value. A full 64-bit result would not fit and would be wrapped in a heap object, which is an allocation. The hash is a small example of the whole design: even the bookkeeping must not make garbage.

Check your understanding

Why is a rectangle just a rounded rectangle with radius zero in this design?

Because every command has the same shape and the renderer draws them all the same way. A rectangle gets parameter = 0 and the shader's corner maths then produces square corners. One code path means one draw call (Part 4).

The list never grows. What happens when a frame has too many commands, and why is that better than growing?

It signals display-list-full. Growing would allocate in the middle of a frame, which is the thing the design forbids, and the error shows the capacity needs raising at the place that caused it.

Why does display-list-hash return only 62 bits?

So the number is an immediate fixnum. A 64-bit unsigned value would be boxed as a bignum on every call.

Which two principles together explain why the display list is allocated once, at a fixed size?

P6 (pay once) and P9 (bound everything). Making the arrays once keeps garbage out of the frame, and a fixed size turns the memory cost into a number you can state and overflow into a loud error. The price is memory held in reserve, about 1.6 MB at the default capacity.

Part 2 of 5 · src/platform/macos/objc.lisp

Talking to Objective-C

Principles at work

P3 Integers, registers and type encodings are conventions. P8 Each message is one direct call with a fixed signature. P6 Selectors and classes are looked up once. P10 Retain, release and the object table decide who keeps what alive. P1 A callback allocates nothing and contains its errors. P2 A test makes a million callbacks and checks the consing.

On a Mac, windows, input, fonts and the GPU are reached through frameworks that Apple wrote in Objective-C. Lisp cannot call Objective-C directly. But Objective-C sits on top of a small C library (the runtime), and SBCL can call C functions through sb-alien (its built-in way to call C). So the core talks to the runtime's C functions and builds everything else on them. This one file is the foundation for Parts 3 to 5.

Many projects solve this with a small C helper library compiled alongside the Lisp. This core uses no C at all, and an early comparison in the project (Spike A against Spike B) found the direct approach allocated nothing per call, while the helper allocated about 700 bytes per frame.

Objects, classes, selectors and messages

Objective-C is built on one idea. You do not call a method. You send a message to an object, naming the message by a selector such as setFrame:display:. At run time the object's class is searched for a method registered under that selector, and that method runs.

The msg-send macro

Everything in the platform layer is written with one macro.

(objc:msg-send :void window "setFrame:display:"
               (:rect 10d0 20d0 300d0 200d0) (:bool nil))

(objc:msg-send :rect window "frame")   ; returns four values: x y width height

The first argument is the result type, then the receiver, the selector string, and each argument as (type value). Because it is a macro, the work happens when the file is compiled:

  • Selectors and classes are looked up once. (objc-class "NSWindow") and the selector string expand into load-time-value forms. The runtime is asked at load time and the compiled code holds the resulting integer. The hot path never searches by name. P6
  • Each call site gets its own fixed signature. Nothing is passed as a variable argument list. Apple's arm64 convention treats variadic arguments (those of functions such as printf that accept any number of them) differently from fixed ones, and objc_msgSend expects the fixed form. P8
  • Objects are plain integers. No alien pointer objects are created. P3

How values reach the function: registers

When one function calls another, the arguments travel in a few named slots inside the CPU called registers. On Apple's 64-bit ARM (arm64) there are separate sets for whole numbers (x0, x1, ...) and for floating-point numbers (d0, d1, ...), each filled in order.

Struct results such as a window's frame are returned through sb-alien and unpacked straight into multiple values.

Memory ownership: retain, release and the pool

Objective-C objects count how many owners they have (reference counting). retain adds an owner, release removes one, and at zero the object is freed. An autorelease pool is a scope that collects objects marked "release me later" and releases them all when the scope ends. with-autorelease-pool wraps this, and code that calls AppKit or Metal runs inside one, as AppKit does for each event. Lisp's garbage collector cannot see Apple's reference counts, so keeping them right is the core's job (P10).

Floating-point traps

By default SBCL raises a Lisp error on some floating-point conditions (invalid operation, overflow, divide by zero). Apple's frameworks hit these conditions during normal work and expect them to be ignored. If SBCL raised an error inside Apple's code, there would be no safe place to catch it. with-masked-float-traps turns those errors off around everything that enters AppKit or Metal.

Going the other way: Objective-C calls Lisp

Sending messages to Apple's classes is half of it. AppKit also needs to call you: when the user clicks, when the window resizes, when it is time to draw. For that it needs a class with methods. Lisp makes one at run time.

view.lisp

(define-callback view-mouse-down sb-alien:void
    ((self sb-alien:unsigned-long) (cmd sb-alien:unsigned-long) (event sb-alien:unsigned-long))
  (let ((view (view-of self)))
    (funcall (metal-view-event-handler view)
             (pointer-event-from-ns-event event self :down))))

(defvar *view-class*
  (ensure-class "AlmightyBoltView" "MTKView"
                :ivars '(("lispSlot" 8 3 "Q"))
                :methods '(("mouseDown:" "v@:@" view-mouse-down)
                           ("keyDown:"   "v@:@" view-key-down))))
  • define-callback wraps SBCL's define-alien-callable, which gives a Lisp function a C address that Apple's code can call (compiled code sits in memory, so like data it has an address). It also catches any error, prints it and returns zero. Letting a Lisp error unwind through Apple's C frames is not safe.
  • ensure-class asks the runtime to create a subclass (objc_allocateClassPair), adds instance variables and methods, and registers it. If the class already exists, because a file was loaded twice, it returns the existing one.
  • The strings like "v@:@" are type encodings. Reading left to right: v returns void, then the first two arguments every method has (@ the object itself, : the selector), then @ one more object. Other letters in use are B bool, d double and Q unsigned 64-bit. A wrong string can crash the process, so these are written carefully.

How a method finds its Lisp data

A callback receives only self, the Objective-C object. The state it needs (the draw function, the event handler) lives in a Lisp struct. Something has to connect the two.

A measured round trip of Lisp, to Objective-C, back into a Lisp callback costs about 23 to 28 nanoseconds and allocates nothing. The test that guards this makes a million callbacks and fails if more than a megabyte is consed (a boxed double each time would be 16 MB).

Check your understanding

Why are classes and selectors looked up with load-time-value?

So the name lookup happens once, when the code loads. After that the compiled call contains the integer. Looking up a string on every call would be slow and could allocate.

A method gets self. How does it reach the Lisp struct for that object?

It reads the integer stored in the object's lispSlot instance variable and uses it as an index into the *objects* table.

What would go wrong if a Lisp error escaped a callback?

It would try to unwind through Apple's C stack frames, which Lisp cannot do safely. define-callback catches the error, prints it, and returns zero.

The rectangle (:rect 10 20 300 200) is passed as four doubles. Why is that equal to passing a struct?

On arm64 a struct of up to four doubles is passed in d0 to d3, which is the same place four separate double arguments go.

Objects are plain integers, so Lisp's collector never sees them. Which principle covers keeping them alive, and what does the core do?

P10. Apple's runtime counts references, so the core calls retain and release itself and wraps work in autorelease pools. An integer is cheap (P3), but nothing about an integer keeps the object alive.

Part 3 of 5 · app, main-queue, window, view, ns-event, event, clock, ring

Windows, views and events

Principles at work

P7 The view draws only on request and the run loop sleeps. P10 Only the main thread touches AppKit. P11 Events are immutable data and time is replaceable. P2 The clock and the ring are the instruments. P9 The ring overwrites its oldest record when full.

Part 2 made it possible to call AppKit and to be called by it. Part 3 uses that to put a window on screen and run the program in response to what the user does.

Who runs the loop?

A normal program has a main that calls things in order. A GUI program inverts that. It starts AppKit's event loop ([NSApp run]), which sleeps until something happens and then calls your code. You are being called, not calling. This is called inversion of control, and it is why Part 2 had to teach Lisp how to receive calls.

An early design note said the core would "own the event loop". In practice AppKit owns the loop, and the core owns frame scheduling: it decides when a frame is requested.

The main-thread rule

AppKit may only be used from the process's main thread. Your REPL, a test runner or a timer will usually be on other threads. main-queue.lisp lets any thread hand a function to the main thread, using macOS's Grand Central Dispatch (GCD), the system's work queue. Touching AppKit from one thread only, and handing it work instead, is P10 by confinement.

Concept: threads and races

A thread is one line of execution inside a program. A program can have several, running at the same moment on different processor cores, and they share the program's memory. That sharing is what makes threads useful and dangerous. If two threads change the same data at once, the result depends on which one gets there first. That bug is called a race, and it comes and goes with timing.

Application, window and view

  • app.lisp. run-application takes a setup function. On the main thread it configures the process as a normal windowed app, installs a menu with Quit, runs setup to make windows, activates the app, and calls [NSApp run], which does not return until the app quits.
  • window.lisp. A window is created with a delegate, an object AppKit tells about the window's life. The delegate's methods turn "resized", "moved to a screen with a different scale", "gained or lost focus" and "closing" into core events.
  • view.lisp. A view is a rectangle of a window that draws and receives input. The core's view is an MTKView (a view backed by Metal) made into a subclass, as shown in Part 2.

The view is configured with setPaused: YES and setEnableSetNeedsDisplay: YES. Normally an MTKView redraws on a timer. These two settings turn that off, so it draws only when request-draw calls setNeedsDisplay:. request-draw is safe from any thread because it goes through run-on-main. This is how the idle window used almost no CPU (P7).

Events: plain data with a timestamp

AppKit's own event objects are converted at once into the core's event structs: pointer, wheel, key, text input, composition (for input methods), resize, scale and focus events. They have these properties:

  • Immutable. Every slot is read-only, so any part of the program can hold one without asking who may change it (P10).
  • Printable. They are made of numbers, keywords and strings, so a recorded session can be written with prin1 and read back as a script. That is the basis for replaying input in tests.
  • Timestamped from the core clock, in nanoseconds.
  • In a consistent space. Positions are in logical pixels from the window's top left (the view claims to be "flipped" so AppKit's bottom-left origin does not leak out). Modifier keys (shift, control, alt, super) are a small bit set of the core's own.

Creating an event allocates a small struct. This happens when the operating system delivers it, outside the frame, so it is not charged to the frame.

The clock and the frame ring

All time in the core comes from one function, now-ns, which reads the operating system's monotonic clock (one that only moves forward, whatever the user does to the date). It is a variable, *time-source*, so a test can swap in a virtual clock that only moves when told to. That makes replays deterministic.

Concept: the ring

A ring (also called a ring buffer or circular buffer) is a fixed-size array used as a log. A position called the head says where the next record goes. After each write the head moves on by one slot, and after the last slot it wraps back to the first. So a full ring replaces its oldest record. Nothing is allocated, moved or deleted, and the ring always holds the most recent records, up to its size.

The frame ring is a ring that holds one record per frame, preallocated. Each record has four numbers: when the frame started, when it ended, and the bytes consed before and after. Recording a frame writes four array slots and allocates nothing, so measuring does not disturb what it measures (P2). The ring also has a fixed size: when it is full the oldest record is overwritten, which is the "drop the oldest" answer to P9. One caution: SBCL's byte counter only advances in chunks of roughly 64 KB, so one frame's allocation reads as zero or a whole chunk. Only totals over many frames mean anything.

Check your understanding

The REPL is on a different thread from AppKit. How does it ask the window to redraw?

It calls request-draw, which uses run-on-main to hand the setNeedsDisplay: call to the main thread through GCD.

Why does an idle window use almost no CPU?

The view is paused and only draws on request, and AppKit's run loop sleeps when it has nothing to do. Nothing in the core runs on a timer.

Why are events plain, immutable structs?

So they can be printed and read back as a script for replay, and so any part of the program can hold one without worrying about it changing.

Why does the REPL hand a function to the main thread instead of calling AppKit itself?

AppKit may only be used from the main thread, and two threads touching the same view at once would be a race. Confining AppKit to one thread, and handing it work through a queue, answers "who may touch this now?" (P10).
