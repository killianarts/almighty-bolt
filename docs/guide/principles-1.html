Principles of fast software, 1: what is true

The goal and the machine. Two principles say what to optimise for and how to know you got there. Three say what hardware is really like. Each is shown in a GUI core, and each reaches well outside it.

Before you start

Every principle is shown in the code of one small program, a GUI core: the layer that turns a list of shapes into pixels on a screen. It must produce a finished picture, a frame, every 16.7 milliseconds (60 a second). You do not have to read the code. The notes headed In the core point to it, and the Core pages explain it when you want it.

Two words come up constantly. To allocate is to ask the language runtime for a fresh piece of memory. In languages such as Lisp, Java and Go, a garbage collector later finds memory nobody uses and frees it, and the program may have to pause while it works. A pointer is a number that holds an address, the position of something in the computer's memory.

The notes headed Elsewhere describe well-known practice in other fields. They are general knowledge, not measurements from this project.

The ideas

Twelve principles of fast software

A rule says what to do. A principle says why it works, and so also says when it stops working. "Never allocate during a frame" is a rule. "When a deadline is fixed, the worst case decides" is a principle. It explains the rule, it predicts that a batch job does not need the rule, and it points to other places that do, such as an audio callback or a web request with a hard timeout.

The twelve principles, on this page and the next, were chosen for reach, David Deutsch's word for how far an explanation extends beyond the case it was first made for. Each one still holds if you change the language, the hardware or the kind of program. Each has four notes: why it is true, how the core shows it, what it costs and where it stops applying, and where else it appears.

No principle is free. Each buys something with something else, usually memory, simplicity or flexibility. A principle taught without its cost turns back into a rule, which is how people end up preallocating everything or caching everything without asking whether it helps.

How the twelve fit together

They are not a flat list. The first two say what you are optimising for and how you will know you got there. The next three are facts about machines. Five strategies follow from those facts. The last two are about organising a project so that the strategies can be applied now and changed later.

Principle 1 · what you optimise for

Judge by the worst case

When there is a deadline, the slowest moment decides how the software feels. The average does not.

Why it is true

A person watching a screen does not experience an average frame. They see every frame. If one misses its deadline (16.7 ms at 60 Hz) the old picture stays up for another refresh and the eye catches the hitch. Frames that all take 8 ms feel smoother than frames that take 2 ms except for an occasional 40 ms one, even though the second set has the better average.

This is the difference between throughput (how much work is done per second) and latency (how long one piece of work takes), and between the average and the tail, the slowest few in a thousand. A deadline makes the tail the thing to manage.

It explains why a garbage collector is a good trade in one program and a poor one in another. In SBCL (the Lisp compiler used here), making a small object is often little more than moving a pointer, so allocation is cheap on average. The expense arrives later, when the collector runs, and while it runs the program is stopped. For a batch job that only has to finish eventually, that is a fair price. For a frame, one stop in the wrong place is a missed deadline.

In the core

The core's first rule, that a frame allocates nothing, is this principle in practice.

  • The display list, the instance buffer and the frame ring are made once, so drawing creates no garbage (Part 1).
  • Nothing in a frame grows. A full display list signals an error instead of being enlarged (P9).
  • At most one frame is in flight, so the GPU cannot fall far behind (Part 4).
  • The frame ring, a fixed-size circular log (what is a ring?), keeps the start, end and bytes consed (Lisp's word for allocated) of each of the last 4,096 frames, so one slow frame shows up and is not averaged away (Part 3).
  • Even bookkeeping obeys it. The hash of a frame is trimmed to 62 bits so that the result stays a fixnum and does not allocate (P3).

The project's charter gives a second reason for the same rule. If the core allocates nothing during a frame, every byte consed in a frame belongs to the GUI library being tested, and the experiment stays honest (P2).

Cost and limits

Reusing storage means holding memory in reserve and accepting hard limits (P6, P9). Code in the frame path has to use typed arrays and declared types, which is less convenient than ordinary Lisp. And the principle only applies where a deadline exists. A build tool or a data job should usually take the collector's convenience and judge by total time.

Elsewhere
  • Web services. Judged by the 95th or 99th percentile response time. A page that usually takes 100 ms and sometimes 3 s is judged by the 3 s, and a request that waits on many servers is as slow as the slowest reply.
  • Audio. Code that runs inside an audio callback avoids allocating and waiting, because one late buffer is an audible click.
  • Runtimes. Low-pause garbage collectors, such as Java's ZGC and Shenandoah, exist because a pause is tail latency.

Try it: the average hides the hitch

A simulation with invented numbers, not a measurement. Each bar is one frame. Frames normally take 2 to 3.5 ms. Now and then a garbage collection lands inside a frame and adds a pause.

Principle 2 · what you optimise for

Measure, and make it repeatable

You can only improve what you can measure, and you can only measure what you can repeat.

Why it is true

Intuition about speed is unreliable. The cost of an operation depends on the hardware, the runtime and the data, and none of them is visible in the code. So a claim such as "this frame allocates nothing" is a guess until a test exists that could show it false.

Measurement also needs repeatability. If a run depends on the real clock, on a person's mouse and on whatever else the machine is doing, two runs differ and you cannot tell whether a change helped. The remedy is to make time and input ordinary values that a test can supply.

Instruments have errors too. A test that cannot fail proves nothing.

In the core
  • The clock, the frame ring and the event structs were written first, before any window existed, so that every later experiment recorded with the same instruments (Part 3).
  • All time comes from one function, now-ns, through a variable that a test can point at a virtual clock.
  • The frame ring records start time, end time and bytes consed for each frame without allocating, so measuring does not disturb what it measures.
  • Tests make a million callbacks or draw ten thousand frames and then check the total bytes consed. A frame can be hashed (Part 1), and the renderer can draw into an off-screen texture to be compared with a stored image (Part 4), so correctness is checked with nobody looking.
  • The two options for reaching AppKit were built and compared on the same acceptance script before one was chosen. The helper library allocated about 700 bytes a frame and the direct bindings allocated none, which was one of the facts in decision record 0007 (Part 2).
  • Two errors in the instruments themselves were found and written into the code. SBCL's byte counter advances in chunks of roughly 64 KB, so one frame reads as zero or as a whole chunk, and only totals over many frames mean anything. And the test framework compiles test bodies under a policy that allocates, so the loops being measured live in separately compiled helper functions.
Cost and limits

Instruments take work before any feature is visible, and they need maintenance. A measurement is a claim about one machine: every number in these pages comes from an arm64 Mac. And measuring can mislead when the thing measured is not what you think it is, as the two instrument errors above show.

Elsewhere
  • Performance engineering. Profilers and benchmarks run before and after every change, and are repeated because one run is noise.
  • Web services. Recorded production traffic is replayed against a new version before release.
  • Testing. A flaky test is a measurement that cannot be repeated. Some databases, FoundationDB among them, are tested by simulating a whole cluster with a fake clock and network, so that any failure can be replayed exactly.

Principle 3 · what machines are like

Everything is bits and a convention

Memory holds only bits. Types, colours, strings and function arguments are agreements about how to read them.

Why it is true

The 32-bit word 3F800000 is the number 1.0 if read as a single-float, the integer 1,065,353,216 if read as an unsigned integer, and the colour (63, 128, 0) with no opacity if read as red, green, blue and alpha. Nothing in the bits says which reading is right. The hardware does not know. Software agrees in advance.

When two components share bytes they must share the convention. For function calls it is called the ABI (application binary interface), for files a format, for a network a protocol. When conventions differ you get either a conversion, which costs time, or a silent bug, such as the UTF-16 index error in Part 5.

This also explains boxing, which is behind the core's first rule. The same number can live as raw bits (in a register, one of the CPU's few named storage slots, or in an array of numbers) or as a pointer to a small cell on the heap, the pool of memory the runtime hands out, holding a header and then the bits. Generic code uses the second form, and making that cell is an allocation. Knowing which form a value has tells you whether using it costs anything.

In the core
  • Values stay in their cheap form. Single-floats and small integers are immediate, stored directly in a machine word, the 64 bits the CPU handles at once. Doubles are boxed. So the display list uses arrays of single-floats, and its hash is cut to 62 bits to stay a fixnum (Part 1).
  • Apple's objects, classes and selectors are plain 64-bit integers. A rectangle is passed as four separate doubles because that is exactly how the arm64 convention passes a struct of four doubles, in registers d0 to d3 (Part 2).
  • The Lisp renderer and the shader agree on a 32-byte instance: which offset holds x, which holds the colour. A colour is one word with red in the high byte. Colours reach the blender premultiplied by alpha, which is a convention about what the numbers mean (Part 4).
  • Core Text counts UTF-16 units and Lisp counts characters, so indices are converted where they cross (Part 5). Y grows downward in the core and upward in Metal's clip space, so the vertex shader flips it.
Cost and limits

Conventions fail silently. A wrong type-encoding string can crash the process, and two sides that disagree about a struct's layout produce garbage with no error. The register rule was verified on arm64 only. Packing several values into one word, as the colour does, saves space but means the parts cannot be named without unpacking.

Elsewhere
  • Text. A page served in one encoding and read as another turns into garbled characters.
  • Networks and files. Two machines must agree on byte order and field layout before a number can cross between them. A file format is a written-down convention.
  • Databases. A column's type fixes how its bytes are read, and changing the type can mean rewriting every row.

Try it: one 32-bit word, five readings

Type a word in hexadecimal, or press a button. Each row is a convention applied to the same bits.

Principle 4 · what machines are like

Arrange data for its reader

Where data sits, and how it is arranged, often matters more than the arithmetic done on it.

Why it is true

A processor can do arithmetic much faster than it can fetch a value from main memory. To hide the gap it keeps recently used memory in small, fast caches, and it fetches memory in blocks called cache lines (128 bytes on this Mac). If the values a loop needs sit next to each other, one fetch brings in many of them. If they are scattered, each costs its own fetch.

So the best arrangement depends on who reads the data and how. A loop that sums every x wants all the x values together. A GPU shader that draws one rectangle wants all of that rectangle's fields together. No single arrangement is best for both. The answer is to give each reader the arrangement it needs and to convert where the data changes hands.

The same thinking chooses the structure for each job: match it to the operation you do most.

In the core
  • In Lisp the display list is a struct of arrays, one typed array per field. An array of single-floats is a block of raw numbers with no header per value, so filling it makes no garbage (Part 1).
  • For the GPU, copy-commands writes an array of structs: a 32-byte record per command with all its fields side by side, because the shader handles one command at a time (Part 4). The figure below shows the change of shape.
  • Structures follow the operation. Adding a command is a counter and some array writes. Finding a shaped line is a hash table keyed by string. Keeping the last 4,096 frames is a ring. Placing a glyph in the atlas is a cursor along a shelf. Finding the Lisp object behind an Objective-C self is an index into a vector.
  • The instance buffer is in shared storage, memory that both the CPU and the GPU can read, so there is no separate upload step. All glyph bitmaps live in one atlas texture, so a frame binds one texture instead of thousands.

The reshaping is cheap. In the devlog's table, encoding and committing a frame grows from about 12 µs at 1,000 commands to about 47 µs at 10,000. The copy is the only step that depends on the count, so it costs roughly 4 ns a command. That figure is calculated from the table, not measured separately.

Cost and limits

Each layout favours one reader and taxes the others. The core could skip the copy by building the display list directly in the GPU's format. It does not, because every part that builds a display list would then depend on the renderer's layout and could not be tested without a GPU (P11). A layout chosen for speed is also harder to read and to change than a list of objects, and it needs type declarations to stay fast.

Elsewhere
  • Databases. A column store keeps each column together, a struct of arrays, and scans one column quickly. A row store keeps whole records together, an array of structs, and fetches one record quickly. An index is a second arrangement of the same data for a different question.
  • Games. Data-oriented design, as in entity-component systems, keeps each kind of component in its own array so that one system can sweep through it quickly.
  • Numerical code. Arrays are stored row by row or column by column, and a loop that walks them in the other order can be many times slower.

Principle 5 · what machines are like

Wide hardware needs uniform work

To go fast on hardware that does thousands of things at once, give it thousands of the same thing to do.

Why it is true

A GPU is thousands of simple workers that share a program. Groups of them run the same instruction at the same moment on different data. They are fast when every worker has the same kind of work, and slow when workers in a group need different instructions, because the group then does both in turn. A CPU's SIMD instructions work the same way on a smaller scale.

So variety should live in data, not in code. A different shape is a different row of numbers, not a different program.

In the core

A GPU draws triangles. The core draws every shape as a quad, a rectangle made of two triangles, and the GPU runs a small program called the fragment shader once for each pixel the quad covers. A draw call is one command asking the GPU to draw a batch of shapes.

  • Every command, whether a rectangle, a rounded rectangle or a letter, is one quad (two triangles) drawn by the same pipeline. A rectangle is a rounded rectangle with radius zero.
  • The command's kind is a field. The fragment shader branches on it, and because the kind is constant across a quad, every pixel of one quad takes the same branch (Part 4).
  • That uniformity is what allows the whole frame to be one draw call (P8).
Cost and limits

The general path costs more than a special one would: a plain rectangle runs the rounded-box formula with a radius of zero. A shape that does not fit the quad-and-distance model, such as a shadow or a gradient, needs a new kind, a bigger record and more shader code. And the principle only helps where there really are many similar items. One large, unique piece of work gains nothing.

Elsewhere
  • Image, audio and video code. SIMD instructions apply one operation to a whole run of values at once.
  • Databases. Vectorised query engines process a column in batches instead of one row at a time.
  • Machine learning. Work is batched into large matrix multiplications, and sequences are padded to equal length so that a batch is uniform.
