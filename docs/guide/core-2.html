Coming from Core 1

A frame is one finished picture, and the GPU is the graphics chip that draws it. Core 1 covered three things you need here. The display list is a flat, preallocated list of drawing commands, one array per field. The core reaches Apple's Objective-C code with one direct call per message, and treats objects as plain integers. And AppKit's event loop calls the core, which draws only when asked. This page turns the display list into pixels. One more word: to allocate is to ask the language runtime for fresh memory, which the garbage collector later frees by pausing the program, so the core avoids allocating inside a frame.

Part 4 of 5 · src/render/metal/

The Metal renderer

Principles at work

P5 Every command is one quad. P8 So the frame is one draw call. P4 The display list is reshaped into 32-byte records. P10 The single instance buffer forces a wait. P6 Shaders are compiled once, at startup. P3 The instance layout and premultiplied alpha are conventions. P12 One frame in flight is the simple choice.

The renderer takes a display list and makes the GPU draw it. To follow it you need a rough idea of what a GPU is.

A GPU in one paragraph

A CPU is a few very capable workers who do one task after another. A GPU is thousands of simple workers who all do the same small task at once on different data. Drawing suits this: every pixel can be computed independently. You give the GPU two small programs called shaders and a pile of data, then ask it to draw.

  • The vertex shader runs once per corner point of a shape. It decides where on the screen that corner goes.
  • The fragment shader runs once per pixel the shape covers. It decides that pixel's colour.

Four more words appear below. A buffer is a block of memory the GPU can read, such as the list of commands. A texture is an image in GPU memory that shaders can sample. A pipeline is the compiled shaders plus the settings for drawing (such as how colours blend), prepared once and reused. A draw call is one command telling the GPU to draw.

Metal is Apple's interface to the GPU. The shaders are written in the Metal Shading Language, which looks like C. The core compiles them from a string at run time, so only Apple's Command Line Tools are needed, not full Xcode. That costs 46 to 50 ms the first time and about 1.4 ms once the system cache is warm. It is paid once, at startup (P6).

One quad per command, one draw call for all

Every command, whether a rectangle, a rounded rectangle or a letter, is drawn as a quad: a rectangle made of two triangles. A GPU draws triangles, so any rectangle is two. A strip of 4 vertices gives you exactly that. The corner for vertex v is simply (v & 1, v >> 1). Giving every command the same shape is P5. Drawing them all with one call is P8.

Getting the commands to the GPU

The renderer makes one Metal buffer up front, in shared storage: memory that both the CPU and the GPU can read (on Apple silicon they use the same physical memory). Each frame copy-commands writes the display list into it through a raw memory pointer, 32 bytes per command. The shader reads the same bytes. Notice the change of shape: the display list keeps one array per field, but an instance holds all of one command's fields together, because the shader handles one command at a time (P4).

Anatomy of a frame

render-display-list does these steps. The Metal objects, in order, are a command queue (a line of work for the GPU), a command buffer (one frame's worth of work), and an encoder (which records drawing commands into it).

  1. Wait for the previous frame to finish on the GPU, if it hasn't, because the next step overwrites the buffer it reads (P10). This is almost always instant.
  2. Copy the display list into the shared buffer.
  3. Create a command buffer and an encoder for this frame's render target.
  4. Bind the pipeline, the instance buffer, the glyph atlas texture, and four floats of frame constants (width, height, scale).
  5. Issue the single instanced draw.
  6. End encoding, present the drawable (the image the window will show), and commit.
  7. Keep the command buffer so the next frame can wait on it.

The shader: shapes by distance

The vertex shader reads a command and places the quad. For a rectangle it makes the quad one pixel bigger than the shape on every side, to leave room for a soft edge. It converts points into Metal's screen coordinates, where both axes run from -1 to 1 and Y points up, so it flips Y.

The fragment shader then decides how much of each pixel a shape covers. A pixel on the edge of a shape is not simply inside or outside. If a shape's edge cuts through a pixel, that pixel should be partly coloured. This is antialiasing, and it is what makes edges smooth. The shader gets it from a signed distance function: the distance from the pixel's centre to the shape's edge, negative inside, zero on the edge and positive outside.

// Signed distance to a rounded box: negative inside, zero on the edge.
float2 q = abs(in.local) - (in.half_size - in.radius);
float d = length(max(q, 0.0)) + min(max(q.x, q.y), 0.0) - in.radius;
coverage = clamp(0.5 - d * in.scale, 0.0, 1.0);   // d in points, times scale = pixels

A plain rectangle is the same formula with radius zero. The ramp is one pixel wide: a pixel whose centre lies half a pixel inside the edge is fully covered, a pixel half a pixel outside is not covered, and anything between gets a fraction. Move the slider to see it.

Try it: one edge across eight pixels

The shape fills everything to the left of the red line. Each pixel's shade is the coverage the fragment shader computes for its centre. The curve below is the function clamp(0.5 - d, 0, 1).

Blending: putting a colour on top of another

When the new colour is partly transparent it has to be mixed with what is already there. The shader returns a premultiplied colour: red, green and blue are already multiplied by alpha (here by the shape's alpha times its coverage). The GPU's blend state is then result = source + destination * (1 - source alpha), called "source over". A worked example, 50% red over white:

StepRedGreenBlueAlpha
Source: red at 50%, premultiplied0.5000.5
Destination: white1111
Result: source + destination × (1 − 0.5)1.00.50.51.0

The result is pink, as it should be. Premultiplied alpha also makes the antialiased edges blend correctly, since coverage and opacity are the same kind of fraction.

For letters, the fragment shader reads its coverage from the glyph atlas texture (Part 5) instead of the distance formula, then applies the same colour and blend.

Rendering without a window

The same renderer can draw into an off-screen texture and read the pixels back (target.lisp). The tests use this to compare a rendering against a stored image, shapes.ppm, with a small tolerance. It is how the project checks pixels without a person looking.

Check your understanding

How many draw calls does a frame with 5,000 commands make?

One. The same four-vertex strip is drawn 5,000 times as instances, and each instance reads its own command from the buffer.

Why does the quad extend one pixel beyond the shape?

So the antialiased edge, which spreads slightly outside the shape's exact boundary, has pixels to land on. Without that margin the edge would be clipped.

Premultiplied red at 25% opacity over white. What are the numbers?

Source is (0.25, 0, 0, 0.25). Result is source + white × 0.75, so (1.0, 0.75, 0.75, 1.0).

Why is only one frame allowed in flight?

The instance buffer is reused every frame, and the CPU must not overwrite it while the GPU is still reading it. Waiting for the previous frame is the simplest way to know it is free. Overlapping frames would need several buffers and a signal for when each is free again, and the usual signal, a completion handler, is an Objective-C block that the core cannot make yet. Waiting is simple and costs almost nothing in practice (P10, P12).

A plain rectangle could be drawn by simpler code than a rounded rectangle or a letter. Why is it not?

Uniform work (P5). One pipeline and one record shape let the whole frame be a single draw call (P8). The price is that a plain rectangle runs the rounded-box formula with a radius of zero.

Part 5 of 5 · src/text/ and the glyph atlas

Text

Principles at work

P6 A line is shaped once and a glyph rasterized once. P3 Core Text and Lisp count characters differently. P4 The atlas packs many bitmaps into one texture. P9 The atlas fails loudly when full, and the line cache has no bound. P10 The cache copies its key.

Text looks easy and is the hardest part of a GUI core. Three jobs are involved. Measuring answers "how wide is this string, and where does a line break?" so layout can work. Hit-testing answers "which character is under this click, and where is the caret for character 5?" And drawing turns letters into pixels. The core uses macOS's own text engine, Core Text, for the first two, so text looks and behaves like text in other Mac apps.

Vocabulary: glyphs, baselines and advances

A glyph is a drawn shape from a font. A string of characters becomes a string of glyphs, but not one for one. Two letters can merge into a ligature, a character can need several glyphs, and a font that lacks a character is replaced for that character by another font. Working that out is called shaping. Shaping also yields each glyph's position.

Fonts, lines and the cache

A font wraps a Core Text font at a size, and keeps its ascent, descent and leading as single-floats, which are immediate values and do not allocate. shape-line asks Core Text to shape a string in a font and returns a text-line: the glyph ids, which font each glyph actually came from, the x and y position of each, and the width, ascent and descent. Shaping a new string costs about 170 microseconds, which is fine once but too slow every frame (P6).

So get-line keeps each font's lines in an equal hash table keyed by the string. A hash table finds the entry for a key without searching: it turns the key into a number that says where to look. A hit costs 20 to 126 nanoseconds and allocates nothing. The cache stores its own copy of the string, so changing the original string afterwards cannot confuse it. It has no eviction yet, so it grows with every distinct string. That breaks P9, and the known-limits list below records it.

The measuring API that layout calls:

(line:measure-text font "Hello")        ; width, ascent, descent
(line:break-lines font text 100)        ; list of (start end) pairs that fit in 100 points
(line:index-at-x line 42.5)             ; which character is at this x (a click)
(line:caret-x line 3)                   ; where the caret sits before character 3
(line:caret-rect line 3)                ; x, y, width, height of that caret

The UTF-16 trap

Core Text counts characters in UTF-16 units, a format in which most characters take one unit and characters outside the Basic Multilingual Plane, such as emoji, take two. Lisp strings are indexed by whole character. After an emoji the two numbering schemes disagree, so every index that crosses the boundary is converted. If it were not, a click after an emoji would put the caret in the wrong place. Type something into this box to see it.

Drawing a letter: bitmap, then atlas

The GPU draws rectangles from textures, so a letter has to become an image first. rasterize-glyph asks Core Graphics to draw one glyph at the display's scale into an alpha-only bitmap: one byte per pixel, 0 for no ink and 255 for full ink. Colour is not stored. The shader applies the text colour later, so one bitmap serves any colour. The bitmap has 2 pixels of padding on each side because the soft edge of the ink reaches slightly past the box that Core Text reports.

Along with the pixels the code keeps two offsets, bearing-x and bearing-y, which say where the bitmap's top left corner lies relative to the glyph's origin on the baseline.

Making a new texture and a new draw call for every glyph would be slow. Instead all glyph bitmaps go into one big grey-scale texture, the glyph atlas (1024 by 1024 pixels, one byte each). A glyph is rasterized the first time it is wanted, copied into a free spot, and its texture rectangle (fractions of the atlas, 0 to 1) is stored in a small GPU buffer. The glyph is then identified by a small integer, its index, and later requests find it in a hash table keyed on the font and glyph id. So the first frame that needs a new glyph pays for rasterizing it inside that frame, and the core does not yet fill the atlas in advance (P6).

Free spots are found with the simplest method that works: a shelf packer. Glyphs are placed left to right along a horizontal strip. When the next glyph does not fit, a new strip starts below, as tall as the tallest glyph on the one before. Try it. This demo uses a 256 by 256 atlas so you can see the strips.

Try it: filling a shelf-packed atlas

Each block is a glyph bitmap of random size. The packer keeps a cursor (x, y) and the height of the current shelf. The same rules as allocate-space.

The atlas never evicts. When it is full, asking for another glyph signals glyph-atlas-full. That is acceptable at this stage and listed under the open items. It is P9, a bound with a loud failure, and P12, a simple choice written down.

From string to commands

Each glyph's position is rounded to a whole pixel before it is pushed. The atlas bitmaps were drawn at exactly the display's scale, and the shader samples them one texel per pixel without blending between neighbours. Without the snapping a glyph would land between pixels and look blurry.

The cost is small. A glyph command takes about 47 nanoseconds to push, and a frame of 4,841 glyphs encoded in about 32 microseconds.

Known limits

  • The line cache and the glyph atlas never evict.
  • Emoji come out as flat, one-colour silhouettes, because the atlas stores coverage only.
  • Glyphs are positioned on whole pixels, not fractions.
  • An atlas is built for one scale. Moving a window between a Retina and a non-Retina screen needs a second one.

Check your understanding

Why does get-line exist?

Shaping costs about 170 µs, far too much to repeat each frame. The cache returns the same text-line for the same font and string in tens of nanoseconds with no allocation.

The string "a😀b" has three characters. At which UTF-16 offset does the caret for index 2 sit?

3. The emoji takes two units (offsets 1 and 2), so "b" starts at offset 3.

Why does one bitmap per glyph work for any text colour?

It stores only coverage. The shader multiplies the command's colour by that coverage.

What does a shelf packer do when a glyph does not fit on the current shelf?

It starts a new shelf below, with height equal to the tallest glyph on the previous one, and places the glyph at its left end. If there is no vertical room left it signals an error.

Name the principle each of these keeps or breaks: (a) the line cache has no eviction, (b) the cache stores its own copy of the string, (c) the first use of a glyph rasterizes it inside the frame.

(a) breaks P9, bound everything. (b) keeps P10: a caller who changes the original string cannot corrupt the cache. (c) is P6 paid lazily. The cost is paid once, but at an awkward moment, which puts P1 at risk for that frame.

Finish

One frame, end to end

Here is the whole path for the moment a user clicks a button, in the order it happens. Each step names the part of the tour that covers it and the principles it shows.

  1. AppKit wakes the sleeping run loop (Part 3). P7
  2. AppKit calls the view's mouseDown:, a Lisp callback (Part 2). It finds its Lisp struct through the object's lispSlot. P3 P8
  3. The callback turns the NSEvent into a pointer-event, stamped from now-ns, and calls the event handler (Part 3). P11
  4. The handler changes the interface state and calls request-draw, which hands a setNeedsDisplay: to the main queue (Part 3). P10 P7
  5. On the next refresh AppKit calls drawInMTKView:, which calls on-draw (Part 3).
  6. on-draw clears the display list, pushes rectangles, and for text calls get-line and push-line, which may rasterize a new glyph into the atlas (Parts 1 and 5). P6 P4
  7. render-display-list copies the commands into the shared buffer, encodes one instanced draw, presents and commits (Part 4). P8 P5 P10
  8. The GPU runs the vertex and fragment shaders and the window updates. The run loop goes back to sleep (Parts 3 and 4). P7

Apart from the small event struct made in step 3, and the first use of a new string or glyph, steps 2 to 7 should not allocate. Where the project has measured it, they don't:

The common path uses a small part of the budget, which is what makes the rare slow event of P1 the thing worth guarding against.

What is not finished

  • Only arm64 has been verified. The way structs are passed would differ on Intel.
  • Focus and scale-change events could not be observed from a background process, because macOS does not activate it.
  • After sustained drawing, an idle window sometimes shows a few wakeups (0, 7 or 26 per 10 seconds). The cause is unknown.
  • Open items include colour glyphs, cache and atlas eviction, drawing a whole run of glyphs in one command, blending in linear light, redrawing only the changed region, several frames in flight (needs more buffers and a signal, usually an Objective-C block), input-method editing, a baseline variant that only replays a display list, and Windows and Linux backends.
