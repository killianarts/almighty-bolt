Teaching this

Each of the five pages stands alone, which gives two sensible orders.

Principles first suits a general audience, for example web developers who will never touch this code. The ideas are the point and the code is the evidence.

  1. Start from the index. Read What a GUI core does aloud, and make sure everyone can say what a frame is and why 16.7 ms is the budget.
  2. Take one principle at a time, on Principles 1 and then Principles 2. Ask the group to predict a decision in the core before showing it, then show the code and the cost.
  3. For every principle ask two questions: what would make this advice wrong? and what does it cost? The answers are under "Cost and limits". A learner who can state them has a principle. One who cannot has a rule.
  4. Then walk the five parts of the tour, on Core 1 and Core 2, in order, using the table on the index as the route.

Code first suits people who will read or change the core. Start at Core 1 and read it in order. Part 1 is a good warm-up because it needs nothing but arrays. Part 2 is the hardest, and everything platform-specific stands on it. Part 3 puts it to use. Parts 4 and 5 are independent of each other once Part 1 is understood. Read the Principles pages afterwards, or whenever a "why" in the tour is unclear.

Name the principle

Show a snippet and ask which principle explains it. Several snippets have more than one answer, and the discussion is the point.

(load-time-value (objc-class "NSWindow"))
Which principle explains this?

P6, resolve early. The name is looked up once, when the code loads, and the compiled call holds an integer (P3).

(when (>= i (display-list-capacity display-list))
  (error 'display-list-full :capacity (display-list-capacity display-list)))
Which principle explains this?

P9, fail loudly when a bound is reached. It also keeps P1: growing the list would allocate inside a frame.

(defun render-display-list (renderer display-list pass drawable width height scale)
  (wait-for-last-frame renderer)
  ...)
Which principle explains this?

P10. The GPU may still be reading the instance buffer that the next line is about to overwrite.

(msg-send :void encoder "drawPrimitives:vertexStart:vertexCount:instanceCount:"
          (:ulong 4) (:ulong 0) (:ulong 4) (:ulong count))
Which principle explains this?

P8: one call for the whole frame, instead of one per command. P5 is what makes it possible, since every command has the same shape.

(setf (sb-sys:sap-ref-single sap offset) (display-list-x display-list i)
      (sb-sys:sap-ref-single sap (+ offset 4)) (display-list-y display-list i)
      ...)
Which principle explains this?

P4. This is the copy that turns one array per field into one record per command, because the GPU reads a whole command at a time.

(ldb (byte 62 0) (logxor hash (ash hash -62)))
Which principle explains this?

P3 and P1. The result is kept in the immediate form, a fixnum, so returning it allocates nothing.

(let ((delta (- (sb-ext:get-bytes-consed) before)))
  (assert-true (< delta 300000) delta))
Which principle explains this?

P2. A claim of "allocates nothing" is made falsifiable by a test that totals the bytes consed over 400,000 lookups. Totals, because the counter moves in chunks.

setPaused: YES
setEnableSetNeedsDisplay: YES
Which principle explains this?

P7. The view stops redrawing on a timer and draws only when a frame is requested.

Exercises that make it concrete

These are suggestions. Not every one has been run.

  • Count the garbage. Run the allocation tests (make test) and read one of them. Then write a small compiled loop that boxes a double on every pass and measure it with sb-ext:get-bytes-consed, the way the tests do. This makes "a frame allocates nothing" real (P1, P2).
  • Break a bound. Make a display list with capacity 10 and push 11 rectangles. Read the error. Then explain why overwriting the oldest record is right for the frame ring and wrong for the display list (P9).
  • Predict, then measure. Before running make bench-metal, write down how you expect the encode time to change as the command count grows from 10 to 10,000. Run it and compare (P8).
  • Read the shader. In rect-pipeline.lisp, change the 1.0 / frame.scale margin to 0.0 and look at the rounded corners in the golden-image test (P2).
  • Trace one message. Pick any msg-send in the repository and write out the registers it fills, using the register diagram in Part 2 (P3).
  • Break the cache. Measure the same string twice with measure-text and time each call, then clear the cache and time it again (P6).
  • Find the cost. Pick any principle and write down what the core pays for it. Compare your answer with its "Cost and limits" note (P12).
  • Run a spike. The Makefile has spike-a to spike-e, bench-metal and bench-text. Each prints its own measurements (P2).

Glossary

TermMeaning
ABIThe agreement about how functions receive arguments and return results, and how data is laid out in memory, so that separately built code can work together.
AllocationAsking the runtime for new memory. Produces garbage that the collector must later free.
Array of structsStoring whole records one after another, so each record's fields sit together.
AtlasOne big texture holding many small images, here the glyph bitmaps.
BackpressureMaking a producer wait when a buffer or consumer is full, instead of letting work pile up.
BaselineThe line letters sit on.
BatchingSending many items across a boundary in one call instead of one call each.
Boxed / immediateA value stored in its own heap cell, or one that fits directly in a machine word.
Buffer (GPU)A block of memory the GPU can read, such as the list of drawing commands.
Cache lineThe block of memory, 128 bytes on this Mac, that a processor fetches at a time.
CallbackA function you hand to other code so it can call you.
Closure, blockA function packaged with the variables it uses. Objective-C calls its version a block.
Display listThe flat list of drawing commands for one frame.
Draw callOne command telling the GPU to draw.
Event loopThe system's loop that sleeps until something happens, then calls your code.
Fragment shaderGPU program that computes the colour of one pixel.
FrameOne complete picture shown on the screen.
Garbage collectorThe part of the runtime that frees memory nobody uses.
GlyphThe drawn shape of a character in a particular font.
Hash tableA structure that finds the entry for a key without searching, by turning the key into a number that says where to look.
HeapThe pool of memory that the runtime hands out pieces of when a program allocates.
Hot path, cold pathCode that runs very often, such as every frame, and code that runs rarely, such as at startup.
InstancingDrawing the same shape many times with different per-copy data in one call.
LatencyHow long one piece of work takes from start to finish.
Machine wordThe amount of data the CPU handles at once, 64 bits on this Mac.
OwnershipKnowing who may use or change a piece of storage now, and who frees it.
Pipeline (GPU)The compiled shaders plus the settings for drawing, prepared once and reused.
Pointer / addressA number naming a location in memory.
PollingAsking again and again whether something has changed.
RaceA bug in which the result depends on which of two threads reaches shared data first.
ReachHow far an explanation extends beyond the case it was first made for.
RegisterA named slot inside the CPU. Arguments to functions travel in registers.
RingA fixed-size array used as a circular log: the head moves on after each write and wraps round, so the newest record replaces the oldest.
SeamA narrow place in a design where one piece can be replaced without touching the rest.
SelectorThe name of an Objective-C message, such as setFrame:display:.
ShapingTurning characters into positioned glyphs, with ligatures, kerning and font fallback.
Signed distanceDistance to a shape's edge: negative inside, positive outside.
Struct of arraysStoring each field of many records in its own array.
Tail latencyThe latency of the slowest few requests or frames, as opposed to the average.
TextureAn image in GPU memory that shaders can read.
ThreadOne line of execution in a program. Several can run at once and share the program's memory.
ThroughputHow much work is done per second.
Vertex shaderGPU program that places one corner point of a shape.
