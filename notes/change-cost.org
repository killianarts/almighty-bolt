#+TITLE: Change-cost tests: the five edits

The charter's change-cost tests (H2): scripted edits applied to each variant, measuring the size
of the diff. This file says what each edit is, before anyone writes it, and how it is counted.
Decision record 0024 has the results. Written 2026-10-26 before the edits were made.

* Method
- Each edit starts from the same base commit and is made on a branch of its own: the edits do
  not build on each other.
- Each edit is first a *specification* and an *acceptance test* that is the same for every
  variant (the driver of =apps/7guis/t/acceptance/= runs it against each). The tests that
  describe the new behaviour fail before the edit, in every variant; a test that guards what
  must not change passes before and after.
- A shared change (the model of a task, the painters that variants share) is made once and
  committed apart. Then each variant's own view code is changed, one commit for each variant,
  in the order given below, and the variant's acceptance tests are run. (E1 to E5 were written,
  all three variants, before any was run, because a benchmark was using the machine; each
  variant's commit is separate and in the order below.)
- The order is rotated from one edit to the next, because the variant that is done first pays
  for finding out what the edit needs, and the later ones are helped by it.
- What is counted, for each commit: the lines of code added and removed (blank lines and lines
  that are only a comment are not counted, and are noted apart), the files and the hunks. The
  tool is =scripts/diff-size.lisp=. Four sums are given for an edit: the tests (shared), the
  shared model or painter, and the code of each variant.
- Where a variant lacks something the edit needs, the cost of making it is counted apart, as
  library code, and the record says so.
- All of it was written by one author (Claude), who also wrote the variants. The rotation of
  the order is the one thing done about that. Whoever scores the usability rubric should read
  the patches, which are kept in =results/change-cost/=, and the notes under each edit of what
  was awkward.

* The edits
** E1. Add a field to the CRUD form
Target: the CRUD app. An Email text field below Surname. Create and Update keep it with the
entry; selecting an entry shows its email; Delete clears it; Create can be pressed when any of
the three fields has text. The list still shows "Surname, Name".
Order: retained, reactive, immediate.

** E2. Make the flight booker's return date optional
Target: the flight booker. For a return flight with an empty return date, Book can be pressed
(an open return) if the start date is valid; the message says "Booked an open return flight
from <start>." An empty return field is not shown as invalid. A return date that is not empty
and is wrong still disables Book and is shown as invalid, as before.
Order: reactive, immediate, retained.

** E3. Add undo to the temperature converter
Target: the temperature converter. An Undo button. Every change that a person makes to a field
(a key typed, a character deleted) is one step that Undo takes back: both fields return to
what they showed before that change. Undo cannot be pressed when there is nothing to undo.
Order: immediate, retained, reactive.

** E4. Hide a group of controls behind a switch
Target: the CRUD app. The row "Filter prefix: [field]" is hidden when a switch says so. There
is no checkbox widget in any variant, so the switch is a choice of two options, "filter on" and
"filter off", standing where a checkbox would. While the filter is off the list shows every
entry whatever the field holds, and the row is not on the screen; the filter's text is kept and
the row comes back with it when the filter is turned on.
Order: retained, immediate, reactive.

** E5. Change the layout of a dialog from vertical to two columns
Target: the flight booker, which is a column of five controls. The kind of flight, the start
date and the return date stay in a column on the left; the Book button and the message go in a
column on the right, beginning at the height of the first row.
Order: reactive, retained, immediate.

* E4 again, with a real checkbox (2026-10-27)
Written 2026-10-27 before the checkbox or the edit exists, on =phase-2= at =6470505=. Micah: "E4
should use a real checkbox." Decision record 0024 (accepted) has E4 as it was made, with a choice
of two options standing where a checkbox would; the text of E4 above is left as it is because
0024 points at it.

** What is different
- The switch is a checkbox labelled "Filter", with the id =:filter-switch=, checked at first (the
  row is shown). A click on the box or on its label toggles it; the space bar toggles it when it
  has the keyboard; Tab reaches it. Unchecked: the row "Filter prefix: [field]" is not on the
  screen, the list shows every entry whatever the field holds, and the filter's text is kept;
  checked again, the row comes back with its text and the list is filtered by it. The checkbox
  stays where it is (above the filter row) in both states.
- The checkbox is a widget that no variant has. It is made first, in each variant, as library code
  with its own tests and its own commit, and counted apart from the edit: that is the "change-cost
  datum of its own" that 0024 said it would be. One interface in the three: retained, a node with
  =checkbox-checked= and an =:on-change= given the new state; reactive, a view with =:checked= and
  =:on-change= (the app owns the state, as it does for the other widgets); immediate,
  =(checkbox id label checked)= returning =(values checked changed)=, as =text-field= does.
- The acceptance tests are the four of E4 with the switch changed: one click turns the filter off,
  another turns it on. They are written first and fail in the three variants before any app is
  changed. The unit tests of the widget (click, space, label, disabled, Tab) are in each variant.

** Base, and what can be compared
- The base is the current tree, whose apps have been ported to the builder macros (record 0026,
  option (a)): the retained apps are 15 lines longer than they were at =c435ab6=. So this edit is
  not like for like with the table of 0024. What is valid is the three variants against each other
  on this base. Whether a real checkbox makes the edit cheaper than the choice did would need E4
  with the choice made again on this base; that is not done here.
- Counted as in 0024 (=scripts/diff-size.lisp=: lines of code added and removed, no blank lines or
  comments, no change of white space): the shared tests, then each variant's app; the library of
  each variant apart, source and tests. Patches in =results/change-cost/e4-checkbox/=. One author
  wrote the variants, the widgets and the edit.
- Order of the variants, rotated from E4's own (retained, immediate, reactive): immediate, reactive,
  retained.

** What I expect
- The library: the retained checkbox is the largest (a node with layout, painting, the pointer and
  the keys: 50 to 70 lines of source), the immediate next (a box kind and its painting and events:
  35 to 55), the reactive the smallest (a view and a node made from the retained one: 15 to 30,
  because the retained node does the work).
- The edit, in lines of code changed in the app: immediate 10 to 14, reactive 12 to 18, retained
  18 to 25; the tests 18 to 24. The retained app is still the largest, because it needs a handle on
  the row to show and hide it; the checkbox saves each variant a few lines over the choice (no list
  of options, no fractions to click at).
- It is wrong, as a statement about the variants, if the reactive library is larger than the
  immediate one, if the immediate app's edit is larger than the retained one's, or if any
  variant's edit comes out more than 26 lines (the largest of the choice's, on the old base).
