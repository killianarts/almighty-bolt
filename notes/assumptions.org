#+TITLE: Assumptions made during the autonomous run
#+DATE: 2026-10-25

Each entry is something that was taken to be true because it could not be checked
while Micah was away. Status is OPEN until Micah has checked it, then VERIFIED or
FALSE. See =notes/autonomous-run.org= for how commits name them and
=scripts/assumption-impact.sh= for finding what rests on one.

Entry format:
- *Statement.* What was assumed.
- *Why not checked.* What stopped it being tested here.
- *Check.* Exactly what Micah can run or look at to settle it.
- *If false.* What to redo.

* A-001 [VERIFIED] Snapshots show what a window shows
- *Statement.* A variant drawn into an off-screen texture by =scripts/snapshot= has
  the same pixels as the same variant in a window, apart from the window's own chrome,
  at the same size and scale.
- *Why not checked.* There is no way to look at a window from here, and the one run
  that compared them (the Counter, 2026-10-25) was Micah's, by eye.
- *Check.* Run =make 7guis VARIANT=retained TASK=counter= (or any other task) and
  compare the window with =design/screenshots/= pictures when they exist.
- *Evidence (2026-10-26, VERIFIED by Micah).* "Windows match." Micah compared the windows
  with the snapshots. The one bug found by looking (text typed into a cell running under the
  cells beside it, A-005) was reproduced in a snapshot first, with the same sliver of a glyph
  at the same place, so a snapshot shows what a window shows there too.
- *If false.* Every visual judgement made from a snapshot is suspect: re-look at each
  task in a window.

* A-002 [VERIFIED] AppKit's characters for the named keys are the documented ones
- *Statement.* In a window, the arrow keys, forward delete, Home, End and Page Up and
  Down arrive as =characters= U+F700 to U+F703, U+F728, U+F729, U+F72B, U+F72C and
  U+F72D; the Delete key arrives as U+007F; Escape as U+001B. Only Tab, Space, Return
  and Shift-Tab have been seen (2026-10-25).
- *Why not checked.* Keys cannot be pressed here.
- *Evidence (2026-10-26, VERIFIED by Micah).* Micah's =LOG=1= runs: the arrows, Home, End,
  Page Up, Page Down and forward Delete arrive as U+F700 to U+F703, U+F729, U+F72B, U+F72C,
  U+F72D and U+F728, as listed. Tab (code 9, physical 48) arrives with and without Shift.
  Escape arrives as code 27 (physical 53). The Delete key (physical 51) arrives as =#\Backspace=
  and deletes backwards in a text field; the log shows the key after =logical-key= has
  translated it, so the raw character (U+007F) is not shown, only that the result is right.
- *Check.* Run any text field task and press each of those keys; the logged variant
  (=make 7guis ... LOG=1=) prints each key down with its character code.
- *If false.* Fix =logical-key= in =core/src/platform/macos/ns-event.lisp= and the
  constants in =core/src/event.lisp=; nothing else knows the codes.

* A-003 [VERIFIED] A printable key's character is the text to insert
- *Statement.* For a key without Command or Control held, the first character of the
  event's =characters= is what typing that key means, including Shift and Option
  characters. Dead keys and input methods are not supported.
- *Why not checked.* Needs a keyboard; composed input needs a second input source.
- *Check.* Type letters, digits, punctuation and shifted letters in a text field.
- *Evidence (2026-10-26, VERIFIED by Micah).* Typing in the text fields "completed, worked
  fine". Dead keys and input methods are still not supported, as the statement says.
- *If false.* A real text-input path (NSTextInputClient) is needed, which is Phase 6.

* A-004 [VERIFIED] The wheel's sign and units
- *Statement.* A =wheel-event= with a positive =dy= means the content moves down (the
  view goes toward the start). Inside the variants the deltas are in lines, and a line is a
  row of a list or a grid (24 points). A wheel gives lines; a trackpad, or a mouse whose
  software smooths its scrolling, gives precise deltas in points, which =wheel-event-lines=
  divides by 24 (0017). The grid scrolls across by 0.3 of a column to a line.
- *Why not checked.* No trackpad or wheel here.
- *Evidence so far (2026-10-26, still OPEN).* Micah's mouse (with the maker's software)
  scrolled the immediate CRUD list by several rows to a notch. The first guess, that it sent
  precise deltas in points which were read as rows, was wrong: the =LOG=1= output shows every
  event =in lines= with =dy= of 3.82 or -3.82, so a notch moves 3 or 4 rows (the 0.82 is
  carried to the next). 3.82 lines a notch is what macOS gives for that mouse and its
  scrolling-speed setting; the list does what the platform says. 0017 (points to lines) does
  not apply to this mouse. Micah says the list moves the way they expect.
  The trackpad (same run, immediate CRUD, =LOG=1=) sends every event =in points=, whole
  numbers of 1 to 5 an event, and a slow movement scrolls the list a row at a time, in the
  direction expected: 0017 works for it. During vertical swipes many events also carry a
  =dx= of +-1 or 2 points (finger drift). The CRUD list ignores =dx=; the cells grid reads it
  and has no axis locking, so a long vertical swipe may move its columns a little (0.3 of a
  column for 24 points). On the cells grid (=LOG=1=, 2026-10-26) the trackpad moved the
  grid diagonally: a calm swipe across carried =dy= of about a fifth of =dx= (=dx -26,
  dy -5=); a flick was clean. Fixed by 0018, which locks a gesture to one axis. Micah then
  swiped on the immediate cells grid and said "swiping looks good" (2026-10-26). Micah's
  =LOG=1= runs of the retained and reactive CRUD with the mouse wheel show the same events as
  the immediate one (lines, 3.82 for a slow notch in either direction, and 9 to 19 lines in
  one event when the wheel is spun fast); no problem was reported with them. Micah then
  closed the entry with two checks left untried (2026-10-26): the mouse wheel on the grid,
  and the trackpad in the retained and reactive variants. The immediate variant was checked
  with the mouse wheel and the trackpad on the CRUD list and the trackpad on the grid.
  The retained variant's trackpad code is the same conversion and lock as the immediate one
  (0017, 0018) but only the tests have run it.
- *Check.* =make 7guis VARIANT=immediate TASK=cells LOG=1= (and crud): swipe across calmly,
  swipe down with a little drift, and flick, and see that the grid moves along one axis; scroll
  with the wheel and the trackpad and read the printed deltas; a notch should move the list by as many rows
  as the printed lines, a trackpad by a row for each 24 points. The direction should be the
  one your system's scrolling gives for the same gesture elsewhere.
- *If false.* The sign: change it in =pointer-wheel= of the list box and of the grid
  (retained) and in the immediate list box and the grid's =scroll=. The size of a line:
  change =+points-per-line+= in =core/src/event.lisp=; the grid's columns follow it.

* A-005 [VERIFIED] The apps behave in a real window as the acceptance tests drive them
- *Statement.* A person using a task of a variant in a window sees what the acceptance
  tests see: they drive each app with the same pointer and key events a window delivers,
  through the fake context, whose text is 8 points a character. The real text engine
  has other widths, so a layout that fits with the fake one might not (a long message, a
  field that is too narrow).
- *Why not checked.* Windows cannot be used from here. Snapshots with the real text engine
  were looked at for the retained Counter, temperature, flight, CRUD, circles and cells.
  =make 7guis-smoke= opened each retained app in a window and saw it idle.
- *Check.* =make 7guis VARIANT=retained TASK=...= for each task; try the things in
  =apps/7guis/t/acceptance/<task>.lisp=. =LOG=1= prints the events that arrive.
- *Evidence (2026-10-26, VERIFIED by Micah).* "The other tasks seem fine." One bug was found,
  in a case the acceptance tests did not cover: text typed into a cell that was longer than
  the cell was drawn full-length at the cell, and the cells beside it, drawn after, covered
  it, so the end of the text and the caret could not be seen. The editor is now drawn over
  the cells beside it, as wide as the text needs, scrolling to keep the caret in view when it
  reaches the edge of the grid. Two acceptance tests, in all three variants, fail on the old
  painter and pass on the new one. It was in the grid's painter, which the variants share.
- *If false.* The window, or the translation of AppKit's events, is wrong somewhere the
  tests cannot see: start from the log.

* A-006 [VERIFIED] Metal scissor rectangles behave as the offscreen tests show in a window
- *Statement.* Clips (0014) render in a window's drawable as they do into the offscreen
  texture the tests read back: same pipeline, same encoder calls.
- *Why not checked.* The tests read back an off-screen texture; the circle drawer's clipping
  has not been seen in a window.
- *Check.* Draw circles of 200 near the edge of the canvas in =make 7guis VARIANT=retained
  TASK=circles= (right-click a circle, drag the slider up): they must stop at the canvas
  edge.
- *Evidence (2026-10-26, VERIFIED by Micah).* The immediate circle drawer in a window, with
  large circles at the right and bottom edges, the left edge and the top right corner: each
  stops at the canvas edge and nothing is drawn over the padding or the buttons (Micah's
  screenshot, =images/19.png= of the session). Only the immediate variant was run for this; the
  retained and reactive drawers append the same clip commands to the same renderer.
- *If false.* The scissor rectangle may have to be in the drawable's pixels at its real
  size, not the points times the scale given to the host: see =copy-commands=.

* A-007 [VERIFIED] The immediate variant sleeps when idle and answers a window's events as the tests drive it
- *Statement.* The immediate variant asks for a frame only when an event could change
  what is shown (a press, a release, a key, a move that changes what the pointer is over or
  happens while a button is down or over a canvas, a wheel over a box that takes it), and
  while the timer runs. A window that is still therefore draws nothing. The pointer is
  where the events say it is, in the window's points, which is where the last presented
  frame's boxes are; a wheel event carries the place of the pointer.
- *Why not checked.* The tests call =handle-event= and =frame= with a fake context; no
  trackpad here. =make 7guis-smoke VARIANT=immediate= opened each app in a window and saw one
  frame drawn and none in the next 1.5 s (the timer draws at the display rate while it
  runs, as intended), which is not the same as the wakeups under =top=. Not checked: those
  wakeups, the hover and press looks, and the wheel in a window.
- *Check.* =make 7guis VARIANT=immediate TASK=counter= (and the others): hover a button
  and press it (it must look hovered, then pressed); leave it still and look at the
  wakeups with =top -l 3 -s 10 -pid <pid> -stats pid,command,idlew= (as for the other
  variants); scroll the CRUD list and the cells grid with the pointer still over them;
  Tab round the flight booker and the CRUD form.
- *Evidence so far (2026-10-26, still OPEN).* Idle wakeups, from =top -l 3 -s 10 -pid <pid>
  -stats pid,command,idlew= with the window open and the pointer not touched, three samples
  of 10 s each (a trailing =+= is top's own mark; what it means was not looked up):
  | App                                              | Samples 1, 2, 3 |
  |--------------------------------------------------+-----------------|
  | immediate app Micah had open (task not recorded) | 1, 2+, 3+       |
  | retained Counter (baseline), started by Claude   | 0, 1+, 3+       |
  | immediate Counter, started by Claude             | 1, 1, 1         |
  An earlier immediate Counter run by Claude showed 0 in its last sample. All are 0 to 3 a
  sample, and the retained variant, which does nothing when idle, shows the same, so the few
  wakeups are the host's or the runtime's and not the immediate variant's.
  With the immediate Counter in a window, Micah watched its CPU in Activity Monitor: it rose
  while hovering, pressing and scrolling the wheel, and dropped back when they stopped; about
  2% with constant wheel scrolling. Frames were not counted, so this says the cost is small
  and that it ends, not which gestures draw a frame. (A wheel over a box that takes the
  pointer, such as the Counter's button, asks for a frame although no widget uses it; the
  retained variant asks only when something scrolled. Not changed.) Not yet checked: that
  the hovered and pressed looks are right in the window, and the wheel in the immediate CRUD
  list and cells grid (the Counter does nothing with it).
  Micah then checked the rest (2026-10-26): the hovered and pressed looks are right, and the
  wheel works in the immediate CRUD list ("everything looks good"). Marked VERIFIED on that.
  Not tried: the wheel in the immediate cells grid, which is the same canvas code. See A-004
  for the wheel's units.
- *If false.* Wakeups: look at the value =enqueue-event= returns for the events it is
  given (=ui.lisp=). A wheel that does nothing: the place in =wheel-event= may be in
  another coordinate system than the pointer's.

* A-008 [OPEN] Saving a file in Micah's editor is seen by the source watcher
- *Statement.* With =HOT=1=, a file saved in Micah's editor changes the open window
  within about a second. The watcher compares a file's write date, and a hash of what it
  holds if it was written in the last three seconds, four times a second, and reports a
  change when the file looks the same at two looks in a row. The tests and the scripted
  runs write the file in place.
- *Why not checked.* An editor that saves by writing a new file and moving it over the old
  one, or that keeps a backup or a lock file beside it, was not tried. A file missing for
  a moment is handled (a test), and the path is the same after the move.
- *Check.* =make 7guis VARIANT=immediate TASK=crud HOT=1=; change a label in
  =apps/7guis/crud/immediate.lisp= and save. The window should show it within a second,
  with =Hot reload: ... changed; loading.= in the terminal. Then save a line that does not
  read: the window stays, and the compiler's message is in the terminal.
- *If false.* =watch-files= in =apps/7guis/common/sources.lisp=: look at
  =file-signature= for what the editor's save changes.

* A-009 [OPEN] An editor's compile of one form calls SBCL's definition hook
- *Statement.* Compiling a definition from a connected editor (Sly's C-c C-c or C-c C-k)
  calls the functions in =sb-int:*setf-fdefinition-hook*= as =eval=, =compile= and =load=
  do, so a window with =run-variant :rebuild= is made again by it (0030).
- *Why not checked.* Not in Micah's Emacs. What was run: Micah's own Slynk, started as Sly
  starts it (=sbcl= with a pipe for input, sent the form that starts the server), driven
  by a script that speaks its protocol and sends what C-c C-c sends
  (=slynk:compile-string-for-emacs=). With a window opened by =open-app=, compiling a new
  =make-crud= made the app again in the open window. C-c C-k (=slynk:load-file=) was not
  run; it is =load=, which was checked.
- *Check.* In Emacs, =M-x sly=, load the systems, =(almighty-bolt-7guis/launcher:open-app
  :immediate :crud)=, change a label in a buffer of =crud/immediate.lisp=, and C-c C-c
  the =make-crud=: the window should be made again.
- *If false.* =watch-redefinitions= in =core/src/redefinition.lisp= sees nothing of what the
  editor compiles; look at what the editor's compile calls (=compile=, =eval= of the
  form, =load= of a temporary file) and which of them sets the function.
