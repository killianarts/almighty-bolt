#+TITLE: 0019 — Input replay: scripts, a player on the virtual clock, a recorder
#+DATE: 2026-10-26
- Status :: proposed

* Context
The charter (Replay) says what replay is: a script of timestamped events and
checkpoints, targets by test id, settled frames only, a virtual clock, and a
recording mode. 0005 put it off until the first variant renders, and three have.
The harness of Phase 3 needs scripted, repeatable input, and the acceptance
tests of 0013 drive apps by hand-written calls that nothing records. What
remains to decide is how the charter's words are built.

* Options
1. Write the player in the host, on the main thread, so that a script drives a
   real window.
2. Write it in the portable core, driving a variant and a context directly, with
   the clock virtual, and leave a window out of it.
3. For the script: Lisp structures printed with PRIN1, or a form of our own made
   of keywords, numbers, characters and strings.
4. For checkpoint hashes: taken in the live session as it is recorded, or made
   afterwards by playing the script.

* Evidence
- Option 2 needs no window, GPU or AppKit, so the tests of the player run
  anywhere, and the same player serves the tests, the harness and a machine
  interface. A window can be driven by the same script later by a host that
  feeds it.
- Printed structures name packages and slots, so a rename breaks every script.
  The form of our own is a plist per event kind with the defaults left out, and
  is short enough to write by hand: =(:pointer :kind :down :target :count-button
  :fx 0.5d0 :fy 0.5d0 :button 0 :buttons 1 :click-count 1)=.
- A hash taken live depends on when the display asked for frames, which a replay
  does not reproduce for an app that animates. A hash made from a replay is made
  under the same clock that checks it.
- Played with the real text engine and no window (=make replay=), each of the
  three example scripts (the counter, the timer, cells with a double click) gave
  the same hash at every one of its checkpoints on a second run, in all three
  variants, and the golden copies passed. That is the charter's condition for
  trusting a measurement.
- The three variants drew the same display list, bit for bit, at every
  checkpoint of the counter and the timer scripts. For the cells script retained
  and reactive agree and immediate does not, though the pictures of the same
  states were the same pixels in an earlier comparison: the hashes are per
  variant, not shared.
- The first run of =make replay= hung. It was SBCL at its prompt after the
  script had finished, because =--non-interactive= was missing, not the player.

* Decision
Options 2, 3 and 4 (made afterwards). =core/src/replay/= has three files.
=script= holds the form (=(TIME FORM)= entries after a header; pointer and wheel
events by place or by =:target= with =:fx= and =:fy=; key, text, composition,
resize, scale and focus events; checkpoints with a name and a hash), reading and
writing with no evaluation, and the translation of events. =player= has
=replay=, which plays a script into a variant with a context, on a virtual clock
that starts at zero: after an event the frame it asks for is built at once,
while the variant keeps asking they come every 16.67 ms, otherwise time jumps to
the next entry; a checkpoint is looked at in a settled frame; it returns the
hashes of all frames and the checkpoints with what was expected and found. A
control the variant does not show is an error. =script-with-checkpoints= and
=freeze-checkpoints= make a golden script from a run. =recorder= notes the
events a variant is given, with the time since the first, and writes a pointer
or wheel event over a control with an id as a place in that control. The
launcher takes =RECORD=path= to write a script when a window closes, and =make
replay SCRIPT=path= plays one, in another variant with =VARIANT=, or freezes it
with =FREEZE=path= after playing it twice.

* Consequences
- Easier: one script drives every variant; a script can be edited by hand; the
  determinism of every variant is a test; the harness has its input.
- Harder: a golden hash is of the machine's text engine as well, so goldens are
  not kept in the repository, only the scripts. Hashes are per variant. A resize
  or scale event changes the context as the host would, by hand, in the player.
- Not done: playing a script in a window; checkpoints of a screenshot or of an
  app's state (only hashes); recording in a window has not been tried
  (=RECORD=); event times of a recording are the platform's, so a
  frame-for-frame replay of a live animation is not promised.
