#+TITLE: 0009 — Variant contract
#+DATE: 2026-10-25
- Status :: accepted

* Context
The charter sketches the variant contract: five generic functions, a =context=,
=request-frame=, and a rule for settling a frame. It is a sketch, not code, and
the =null= baseline variant cannot be built until it is code. Turning it into
code raises questions the sketch does not answer:
1. Where does the contract live, and what may a variant import? The header of
   =core/src/package.lisp= defers this to this record.
2. What does =context= hold? In particular, how does a variant measure and draw
   text when the text code (=text/=) and the glyph atlas (=render/metal/=) are
   Darwin-only and one of them drives the GPU?
3. What is one frame, in order, and which parts are timed apart?
4. What causes a frame, and what does =request-frame= do?
5. What do the three generics other than =frame= need to do before a variant
   implements them?

This record proposes answers and stays /proposed/ until the =null= variant has
run against them, because almost none of it has been exercised.

* Options
For where a variant gets text:
1. Variants import the text and render modules and call them.
2. The =context= supplies text operations that the host implements, so a variant
   imports only the portable core.

For how events reach a variant:
1. =handle-event= is called for each event as the platform delivers it, on the
   main thread, in order.
2. Events are queued and drained at the start of a frame, as the charter's
   platform-layer sketch says.

* Evidence
Devlog entries of 2026-10-24 and 2026-10-25, and the code.
- =push-line= (=render/metal/draw-text=) takes the glyph atlas, which belongs to
  the Metal renderer, and a =text-line=, which Core Text produces. =text/= and
  =render/= are =:if-feature :darwin=. A variant that called them would call the
  GPU's module and could not run elsewhere. This is the reason for option 2 of
  the first pair.
- Spike B from a terminal: the time to get the drawable ranged from 84 us to
  5,253 us across runs while encoding and committing stayed at 95 to 150 us. A
  baseline that reports one number would mostly report how long the display kept
  us waiting. Build, drawable wait and encode are therefore timed apart.
- The same runs: dragging the window made 271 reshape callbacks and 102 draws
  that nothing in our code requested. AppKit calls draw for a resized view even
  though the view is paused. A host has to build a frame whenever its draw
  callback runs.
- =request-draw= (=platform/macos/view=) calls =run-on-main= with a new closure
  each time, which allocates. =run-on-main= runs the thunk at once when called
  on the main thread.
- The ring (=core/src/ring.lisp=) records four words a frame: start, end and the
  bytes consed before and after. The display list has no operation to copy one
  list into another.
- AppKit already delivers events one at a time on the main thread. A queue
  would add a second place for them to wait, and a still window has no draw
  callback to drain it, so the host would have to request a frame to drain it.
- How other frameworks deliver events (read from their source and docs on
  2026-10-25 through a page-summarising fetch tool, and in part: the GPUI and
  RAD Debugger files were only partly read):
  - Flutter handles each pointer event as its packet arrives. It queues only
    while the binding is locked. A hit test on pointer-down fixes the targets
    for that pointer, and a gesture arena picks the winner. Resampling events to
    frame time exists and is off by default.
  - GPUI's platform callback calls =Window::dispatch_event= at once. A mouse
    move only stores the position. Targets come from hitboxes of the last
    rendered frame, and listeners run in a capture phase and then a bubble
    phase. A frame follows only if a handler marks the window dirty.
  - RAD Debugger (Fleury) gives the UI a list of the frame's events. Each widget
    reads its press, release and drag from the list as it is built, and removes
    the events it handled so later widgets never see them. It tests against box
    rectangles left from the previous frame.
  - Blink's compositor thread queues input for the main thread, and the queue
    can dispatch input aligned to the frame. I read only the header, whose
    comments do not state the coalescing rules.
  - Dear ImGui (1.87) queues events from its backends and spreads conflicting
    ones, such as a press and release in one frame, over several frames so none
    is lost.
  - winit merges duplicate redraw requests into one event.
  - Blick (a video editor written in Odin) has no public source, and its one
    blog post covers caching, not input, so it is not in this list.
  Frameworks that share a thread between events and drawing, and act in
  handlers, handle events on arrival. Frameworks that rebuild the UI every
  frame, or take input on another thread, batch events for the frame. GPUI and
  RAD Debugger both answer hit tests from the previous frame's geometry.
- Measured on SBCL, 2026-10-25, with the first code of the contract
  (=core/src/variant.lisp= and =settle.lisp=): delivering 5,000,000 events
  through the generic function =handle-event= and requesting a frame for each
  consed 0 bytes after warm-up. Settling 1,000,000 frames, which is 2,000,000
  calls to the generic function =frame= that each append 20 commands, consed 0
  bytes, at about 270 ns a build. The variants were ordinary =standard-class=
  instances. Other Lisp implementations are not measured.
- Measured on SBCL, 2026-10-25, with the ring and display-list changes: the
  frame ring record is eight words (a 4,096-record ring is 256 KB), and
  recording a frame with its phases takes about 4 ns and allocates nothing.
  =replace-display-list=, which copies one display list into another, takes
  about 1.9 ns a command (9.4 us for 5,000 commands) and allocates nothing. That
  copy is all the =null= variant's =frame= will do.
- Measured on SBCL, 2026-10-25, with the macOS host and the =null= variant in a
  window (=make bench-null=, two runs, from a shell the agent started): 300
  requested frames, all drawn, each in one refresh (16.6 ms); nothing drawn in
  two seconds of stillness; 0 bytes consed in the draw path. A frame took 180
  and 207 us on average: 14 and 16 us to build (here, copying a list of 221
  commands), 44 and 52 us of waiting (one frame of 300 waited over a millisecond
  in each run) and 122 and 139 us to encode, commit and present. The core's own
  cost, build plus encode, was 136 and 155 us. A request made from inside a draw
  callback, after the frame was presented, was honoured: 101 frames asked for
  one after another were drawn in 1.67 s and 1.66 s, 16.5 ms each, and the
  process consed 0 bytes meanwhile. The host wakes the view with a function made
  once, because =request-draw= makes a closure on every call; the first version
  of the host used =request-draw= there, which the ring could not have seen,
  since the call comes after the record is written, so a test now counts it with
  the whole process's allocation. Spike B showed the wait varying a great deal
  between runs, so two runs are not a distribution.
- Measured on SBCL, 2026-10-25, the same bench three times from a terminal of
  Micah's own: twice with the mouse still (2 and 1 events reached the variant)
  and once with it moving over the window (429). Every run drew 300 of 300
  requested frames, drew nothing in two seconds of stillness, drew 101 of 101
  chained frames in 1.66 to 1.68 s, built every frame once, never hit the cap,
  and consed 0 bytes in the draw path and over the chain. The core's own cost
  was 155, 131 and 141 us, and the GPU took 263 to 266 us a frame. The wait did
  not hold still. "Request to start" is the time from the request to the frame
  beginning, which is the latency minus the whole frame:

  | Run                        | Wait, mean | Over 1 ms  | Request to start |
  |----------------------------+------------+------------+------------------|
  | agent's shell, mouse still |      44 us |   1 of 300 |          16.4 ms |
  | agent's shell, mouse still |      52 us |   1 of 300 |          16.4 ms |
  | own terminal, mouse still  |   1,035 us | 186 of 300 |          15.4 ms |
  | own terminal, mouse still  |  13,843 us | 263 of 300 |           2.8 ms |
  | own terminal, mouse moving |      76 us |   2 of 300 |          16.4 ms |

  Every run took 16.6 to 16.8 ms from request to draw, and 16.5 to 16.6 ms for
  each chained frame, so the wait moves the time and does not add to it. By
  that subtraction the frame in the 13.8 ms run began about 2.8 ms after the
  request (the bench polls every half millisecond) and the main thread then sat
  in the wait, which reached 34 ms (two refreshes) at most; in the others the
  time passed before the frame began. Why is not known. The two slow runs were
  mouse-still runs in Micah's terminal, and spike B hinted the same, but the
  two mouse-still runs from the agent's shell were fast, so holding still does
  not explain it. It is five runs.
- Not measured: what kinds of event the 429 were (the counter does not say, and
  keyboard and scale-change events have not been seen by this host in a window);
  the cause of the wait; and whether the contract is enough for a real variant,
  since none exists yet.

* Decision
Implement the charter's contract as sketched, with the following answers.

*Files and imports.* The contract is two portable files, in the style of 0006:
=core/src/variant.lisp= (the generic functions, their defaults, the =context=
structure and the text operations on it) and =core/src/settle.lisp= (the frame
sequence). They import only =clock=, =ring=, =event= and =display-list=, and
nothing from =platform/=, =render/=, =text/= or =sb-*=. The macOS host goes in
=core/src/platform/macos/host.lisp=. The umbrella package re-exports the
contract; the platform, text and renderer packages stay out of it. A variant
imports only the umbrella.

*The generic functions.*
- =(handle-event variant event)=: true if a frame is wanted. Default: false.
- =(frame variant context display-list)=: appends commands to an empty list;
  true if app state changed during the build. No default; a variant must
  provide it.
- =(hit-target variant x y)=: a stable id (anything comparable with =eql=) or
  NIL. Takes two single floats, not a point object. It answers for the last
  frame that was presented, as hit tests do in GPUI and RAD Debugger, so an
  event that arrives between a state change and the next frame sees the old
  geometry. Default: NIL.
- =(lookup-target variant test-id)=: the rectangle of the target, as four values
  (x, y, width, height), or NIL. Default: NIL.
- =(accessibility-tree variant)=: a stub that returns NIL until H3 needs it.

*Events* go to =handle-event= as the platform delivers them, one at a time, in
order, on the main thread. The core does not queue them. If it returns true the
host asks for a frame.

The core owns the translation of operating-system events into its event
structures, their order, the thread they arrive on, frame scheduling, and
recording and replay. A variant owns everything that an event /means/: which
widget receives it, whether it is consumed, what state changes, focus, and
gestures. A variant that acts on arrival (a retained or reactive one) does its
work inside =handle-event=. A variant that rebuilds its widgets every frame (an
immediate-mode one) appends the event to a list of its own in =handle-event=,
returns true, and has its widgets read and remove events from that list during
=frame=. The cost of that list is then part of that variant's measured cost.
Because the settle loop may call =frame= up to three times for one frame, such a
variant must remove an event when a widget handles it, so that a second build
does not handle it again, and must keep the events no widget handled for the
next frame. Hit-testing and focus primitives are not decided here; they are the
first item of Phase 2 and get their own record when the first variants show what
they need.

*The context* is one structure, made by the host and updated in place, never
made per frame. It holds the size of the drawing area in points, the scale, the
frame number, the number of the build within the frame, and the clock (the core
clock, which replay can replace). Text goes through operations on the context
that the host implements: get a font by name and size; measure a run; break a
paragraph to a width; find the caret for a point and the rectangle for a caret
(the measurement API of 0003); and append a shaped line to the display list.
Their lambda lists are fixed in the code and kept to what the first variants
need. The charter's "frame's instrumentation scope" is narrowed: the frame ring
belongs to the host, and variants write to it only once Phase 3 defines phases.

*The frame, in order.* The host builds a frame whenever its draw callback runs,
whether a frame was requested or not.
1. Read the size and the scale into the context. Start the frame's record.
2. Settle: clear the display list and call =frame=, and repeat while it
   returns true, up to three builds. A frame that reaches the cap logs the
   frame number and presents its last build.
3. Wait for the previous frame's GPU work, then ask the view for its drawable.
4. Encode, commit and present.
5. Close the record.
The variant's work is finished before the drawable is asked for. The ring record
grows to hold the build time, the wait for the display (the previous frame's GPU
work, then the drawable) and the encode time apart, the number of builds, and
whether the cap was hit.

*Requesting a frame.* =request-frame= may be called from any thread, and many
requests before a frame make one frame. While a frame is being made, a request
only sets a flag, and the host asks for the next frame once this one is
presented. At any other time the host asks at once: directly on the main thread
(including from inside =handle-event=), and through the main queue from another
thread. The call that asks does not allocate on the main thread. A variant never
runs its own loop.

*The =null= variant* lives in =variants/null/=. Its =frame= copies a precomputed
list into the frame's list, and its =handle-event= counts events and asks for no
frame. =display-list= gains an operation that copies one list into another
without allocating (=replace-display-list=).

Not decided here: timers, clipboard, IME hooks, several windows, phases a
variant defines, the unsettled-frame opt-in the charter allows (added when a
variant asks, with its own record), the shape of the accessibility tree, and
targets that are not rectangles.

* Consequences
- Easier: a variant imports one package and cannot reach the GPU; the settle
  sequence runs and is tested with no window, no GPU and a virtual clock; the
  baseline reports build, drawable wait and encode as separate numbers.
- Harder: the ring record grows and its tests change; the text operations on the
  context commit the core to the measurement API of 0003 as generic functions;
  the host owns the loop, so a variant that wants its own timing (a game loop)
  needs the unsettled-frame opt-in first.
- Gives up: variants calling the text and render modules directly; variants
  writing their own phases into the ring before Phase 3; a core-owned queue of
  events that could coalesce a 1 kHz mouse (revisit if handling each move costs
  a visible share of a frame). A variant that wants a per-frame event list
  writes its own, or the core offers a small shared one once a second variant
  wants the same code; nothing is built for that yet.
- The draw callback runs on the main thread, and the wait for the drawable is
  inside it. In one run the main thread spent 13.8 ms of each 16.6 ms in that
  wait, and an event that arrived then would be delivered when it ended: "on
  arrival" means when the main thread gets to it (delivery time was not
  measured). Accepting this record fixes the order in "The frame, in order",
  including that wait at step 3. Moving it later or off the main thread would
  need a new record that supersedes step 3, and none is proposed until a
  variant needs the latency.
- To check before accepting: done, and in Evidence: the null variant from a
  terminal of Micah's own with the mouse moving once, =setNeedsDisplay:= from
  inside a draw callback, and the cost of calling =frame= and =handle-event=
  through generic functions. Left: whether the contract is enough for a real
  variant, which only the first one can say.
