#+TITLE: 0021 — The benchmark harness: replay, samples, result records
#+DATE: 2026-10-26
- Status :: accepted (Micah, 2026-10-26)

* Context
Phase 3 starts with the harness. The charter's protocol says: the same machine
and settings, a warm-up with the first runs discarded, every run driven by a
recorded input script, at least ten repetitions with the median and the spread
reported, and differences within the spread treated as ties. A result record is
one file for a run, with the commit, variant, app, machine, date, raw samples
and summary, never edited, only superseded. The metrics include frame time (p50,
p95, p99, max), builds per frame and cap hits, allocation per frame and garbage
collection time. Replay (0019) gives the input and the virtual clock.

* Options
1. Measure in the real host, with a window or an off-screen target, so that a
   frame is what the host's frame timer says: the build, the wait for the
   display, the encoding.
2. Measure the variant's build alone, headless, with the real text engine, by
   timing the settle loop inside the replay player.
3. For the first frame of a run: keep it in the samples, or report it apart.
4. For the record: one file for each variant, app and script, with every
   repetition's raw samples, or one file with only the summary.

* Evidence
- Option 1 needs a display, and its numbers include the GPU and the compositor, which
  are the same for every variant; the question the experiment asks is what the
  variants add. The host records the build, the wait and the encoding in its ring
  already (0009), so the other phases can be joined later; the build is the phase that
  differs.
- Option 2 runs in the same process as the tests, takes a few seconds a script, and is
  deterministic as to what is drawn: the harness stops with an error if two repetitions
  draw different frames, which is the charter's condition for trusting a measurement.
- The first frame of a run is not like the others. The immediate variant builds its
  tables and pools in it and allocates about 1.65 MB there and nothing in the frames
  after it, and every variant's first frame is slower. Mixed into the samples, the
  first frame made the immediate counter script allocate 139 KB a frame in a short
  run.
- Bytes consed read from SBCL's counter move a region at a time, so a frame's bytes are
  only good summed over many frames.
- First results (this machine, 10 repetitions after 3 warm-ups; medians of a frame's
  build after the first, in microseconds; builds a frame, mean):
  | Script         | Retained    | Reactive    | Immediate   |
  |----------------+-------------+-------------+-------------|
  | counter-clicks | 0.6 (1.00)  | 0.7 (1.00)  | 1.8 (1.91)  |
  | timer-reset    | 1.0 (1.00)  | 1.5 (1.00)  | 2.3 (1.02)  |
  | cells-edit     | 13.5 (1.00) | 15.1 (1.00) | 31.4 (2.00) |
  The immediate variant differs from the other two by more than the spread of the
  repetitions' medians in every script; the retained and reactive variants are tied or
  close to it on the counter (0.6 to 0.7 against 0.7 to 0.8) and differ a little on the
  others (13.5 and 15.1, 1.0 and 1.5).
  Steady frames allocate nothing in the counter and cells scripts in the retained and
  immediate variants; the timer allocates 0.8 KB a frame in those and 1.4 KB in the
  reactive one.

* Decision
Options 2, 3 (apart) and 4. =core/src/stats.lisp= has the median, the
percentiles and a summary. =replay= takes =:measure=, which notes for each frame
the real nanoseconds of its build, the builds it needed and the bytes consed,
and for the replay the bytes consed and the garbage collection time.
=bench/results.lisp= (=make bench-run=) plays each script of
=apps/7guis/replay/= in each variant, REPS (10) times after WARMUPS (3)
warm-ups, each in a new variant, and stops if the frames differ from one
repetition to the next. It writes
=results/<date>-<commit>-<variant>-<app>-<script>.sexp=, with the raw samples of
every repetition, the machine, and a summary of the frames after the first
(median, p95, p99, max, the median of each repetition and the spread of those,
builds, bytes a frame) and of the first frame; =make bench-report= prints the
latest of each. The records are kept in the repository.

* Consequences
- Easier: one command gives every variant's numbers on the same scripts,
  repeatable, and an experiment's numbers can be cited by file.
- Harder: this is the variant's build only. Not covered, and left for later: the
  host's phases and the frame timer (frame time as the charter defines it),
  startup, idle CPU and wakeups, memory, image size, compile time, trace output,
  the phases inside a variant's build (layout, record), and a CI run. A
  machine's record is compared with the same machine's.
- Open: scripts long enough that the variants differ in more than a few frames.
  The three examples are short, which is why their medians are of tens of
  samples a repetition.
