#+TITLE: 0030 — Hot reload: compiling code changes the open window
#+DATE: 2026-10-28
- Status :: proposed

* Context
Micah, 2026-10-28: "I definitely want hot reloading." The bar: start a GUI by
running some Lisp, edit and compile the GUI code, and the window changes while
it is open, with no other work.

None of the 7GUIs apps met it. Each builds its UI in a closure that its
constructor makes once, so recompiling the constructor changes nothing in an
open window. A function held as =#'name= keeps the old code too: the registry
did, and so would =(make-immediate-variant #'view)=. An idle window draws
nothing (the core's rule), so a recompile that did reach the code would not be
seen until something asked for a frame. And =run-variant= returned nothing a
REPL could hold, so there was nothing to ask with.

A probe (a window, a second thread that recompiles, a look at what is on screen)
gave:

| UI handed to the variant             | after compiling | after a nudge       |
|--------------------------------------+-----------------+---------------------|
| immediate, =(lambda () (view))=      | no change       | request-frame: new  |
| immediate, ='view=                   | no change       | request-frame: new  |
| immediate, =#'view=                  | no change       | request-frame: old  |
| reactive, thunk calls =(view)=       | no change       | signal write: new   |

* Options
1. Only ask for a frame when code is compiled. Works for an app whose UI is a
   global function called by name, with its state in globals. No app is
   written so, and a retained tree is never described again.
2. Make the app again and swap it in. The registered constructor is called
   again, and the variant it returns takes the place of the running one in the
   same window. Works for every app as written, in all three variants. The
   new app starts from nothing.
3. Make it again and carry state over, by id or from state the app declares.
   Needs a convention for where an app's state lives, and the variants differ
   in where that is (nodes, signals, the application's own variables).

* Evidence
- SBCL calls the functions in =sb-int:*setf-fdefinition-hook*= with the name
  of every function defined or redefined, from a compiled file, =eval=,
  =compile=, or a single form: =defun=, =defmethod= and =(setf f)= functions
  (checked); =defmacro= does not. SBCL also defines its own functions while a
  program runs, so names in =SB-= packages and methods of such generics are
  ignored. No polling is needed to know that code changed.
- A file defines many functions, so the call waits until the definitions have
  stopped for 0.15 s and is made once.
- The new variant is swapped in on the main thread, between frames. If its
  first frame signals an error the old one is put back and the frame is made
  again with it, so code that does not work yet does not take the window with
  it. If the constructor fails the old one stays. Both say why on the error
  output.
- In a real window, with edits made by a script (the file written, the rest
  untouched), in each variant, three rounds each, nine runs: a saved file
  adds a button to the open window in 0.46 to 0.55 s; an edit that compiles but
  fails when the app runs leaves the old app and prints the error; an edit
  that does not read changes nothing; the fixed file shows its buttons.
- On the real tree, as =make 7guis ... HOT=1= loads it (the launcher, the
  variant's apps and the stress apps, so the whole watch list), an edit to the
  CRUD file of each variant, made twice (a label given an id, then the file put
  back), three variants, two rounds: one remake for each save, 0.53 to 0.67 s
  from the write to the new window. The app was then used (a click and typing
  in three fields, and the Create button): 18 more frames in each, and no
  remake.
- A system loaded again compiles a file while it defines nothing, and that can
  take longer than the quiet time, which would remake the app from half of the
  files. The source watcher holds the redefinition watchers until its load is
  done (=with-redefinitions-held=), and they call once after. The real files
  compiled fast enough not to need it; it is there for a file that does not.
- ASDF takes a compiled file for current unless its source is newer by a whole
  second, so a file saved in the second it was compiled in would be missed.
  This happened in the probe's own runs. The compiled files of the files that
  changed are deleted first. A test fails without that.
- The retained constructor builds the tree eagerly, so a broken edit fails
  when the app is made; the immediate and reactive ones fail in the first
  frame. The window keeps the old app either way.
- Micah runs Lisp from Emacs with Sly, which starts =sbcl= with a pipe for
  standard input, sends it the form that starts Slynk, and then sends nothing:
  the main thread is left waiting to read, and the REPL's forms run on Slynk's
  worker threads. A script that speaks Slynk's protocol to Micah's own Slynk
  (started the way Sly starts it) did: open the window from a worker thread,
  which returned in 0.1 s with the main thread running the loop; compile a
  definition with =compile-string-for-emacs=, which is what C-c C-c sends, and
  the app was made again in the open window; close the window and the process
  and the Slynk connection were still there; open it again; and
  =slynk:quit-lisp= with a window open ended the process. With the loop's
  interruption run with interrupts off, that last one hung for more than 45 s.
- AppKit ends the process when the last window closes or Command-Q is pressed
  (=terminate:= calls =exit=). That is right for =make 7guis= and wrong for a
  Lisp that someone is working in.

* Decision
Option 2 now. Option 3 is left until Micah wants state kept, and is better
made with the variants than before them.
- =almighty-bolt-core/redefinition=: =watch-redefinitions=,
  =stop-watching-redefinitions= and =with-redefinitions-held=, the only file
  that knows of the hook.
- The host (=platform/macos/host=): =swap-variant=, =reload-host=,
  =running-host=, and =run-variant ... :rebuild fn=, which watches
  definitions and swaps in what =fn= makes. The variant contract is not
  changed.
- The 7GUIs registry takes the name of a constructor, not the function, so a
  constructor that was compiled again is the one called. All 37 registrations
  changed.
- =open-variant= (the host) and =open-app= (the 7GUIs launcher) open the
  window from another thread and return its host at once: the call interrupts
  the main thread, which runs the window's loop for as long as the window is
  open. Closing the window, Command-W and Command-Q stop the loop and leave
  the Lisp running; =close-variant= and =close-app= do the same; the call can
  be made again. The app is made again when code is compiled, as with
  =run-variant :rebuild=, which stays for a program that is only the window.
- =make 7guis VARIANT=v TASK=t HOT=1= also watches the source files of the
  loaded systems (a thread that looks four times a second, and when a file has
  changed and looks the same at two looks in a row, so that one being written or
  saved in two steps is not loaded half done, loads the systems through ASDF).
  It is for someone who edits in a program that does not compile into the
  running image.

* Consequences
- Easier: edit, save, and the open window shows it in about half a second, in
  all three variants, with no change to any app but its registration.
- Harder: the new app starts from nothing, so typed text, the selection and
  the scroll are lost at every reload. Every redefinition anywhere reloads
  the app, so compiling an unrelated helper does too.
- Harder: a function held across a reload as =#'name= keeps the old code. An
  app that wants hot reload without being made again can pass a name:
  =(make-immediate-variant 'view)= (the probe's third row of the table above).
- A changed macro reaches its users only through ASDF (the saved-file route);
  compiling the macro's form alone leaves them as compiled.
- =HOT=1= wakes a thread four times a second, so a measurement of idle
  wakeups must not use it.
- =open-variant= must be called from a thread other than the main one, and
  needs the main thread to be waiting for something, as it is when Lisp is
  started by an editor with a pipe for input. A Lisp whose REPL runs on the
  main thread (=sbcl= in a terminal) cannot use it: it gets an error that says
  so, and can use =run-variant=.
- Each window that is opened and closed leaves its =NSWindow= and view
  behind. A window opened a few dozen times in a session does not matter.
- What the app prints when it is made again, and what its callbacks print when
  they fail, goes to the output of the thread that opened the window. Under
  Sly that is the REPL buffer if it was opened from there, and the process's
  own output if it was opened from a source buffer.
- Not checked: that Micah's editor's way of saving is seen by the watcher
  (A-008), and the whole in Micah's own Emacs (A-009 has what was run).
