#+TITLE: 0025 — Stress apps: the dashboard, the million rows and the text editor
#+DATE: 2026-10-26
- Status :: proposed

* Context
Step 3 of Phase 3: three apps that the seven small ones do not stress, each in
all three variants. An animated dashboard (frames that never stop; 36 tiles and
a chart that change every frame), a list of a million rows (the text engine and
the scroll, with nothing kept for rows that do not show), and a text editor on a
document of 20,000 lines (editing, selection, scrolling, and text from the input
method of the system). The editor needed the input-method hooks first; they were
built and tested before it (commit 0563338).

What each app is for: H1 says the approaches differ in code size, change cost
and allocation more than in speed; the stress apps give those three something to
show on more than a button. H3 says retained structure makes accessibility, IME
and machine access easier; the editor is the first datum on IME. Neither is
settled here.

* What was done
- Each app has what all three variants share (the model of the data, the painter
  that makes the display list, for the editor the controller that says what an
  event does) and, apart, each variant's own file: how it builds the screen,
  holds the state and learns of a change. The rows and the editor are one canvas
  each, drawn by the shared painter; the dashboard's 36 tiles (a name, a value
  and a bar) are each variant's own widgets and only its chart is a canvas.
- The dashboard is 36 tiles in a grid and a chart of the last 240 steps of three
  series, all from a model that is a function of the time and that takes a step
  every frame; the rows are made from the index when drawn (a million are never
  kept); the editor holds the text in a gap buffer with an index of the lines, a
  selection, a desired column, a composition from the input method, and a status
  line.
- Each app has unit tests of its shared parts and the same acceptance tests for
  the three variants (the driver of the 7GUIs). The editor has 28 unit tests
  (714 assertions; the gap buffer is checked against plain strings over 600
  edits, with the line index made again from the string after each) and 15
  acceptance tests in each variant (189 assertions). The line cache, the
  rectangle given to the input method and the status memo were each broken on
  purpose and the tests failed.
- Replay scripts for each (=apps/stress/replay/=, made by
  =scripts/make-stress-scripts.lisp= so that every variant is driven the same):
  =dashboard-run=, =rows-scroll= (215 entries) and =editor-session= (394: typing
  as keys and as text, lines broken, selection, pages, the wheel, five
  compositions, a drag over lines).
- Found and fixed on the way: the text engine's cache of laid-out lines was
  unbounded, so scrolling the million rows grew the heap with every row that was
  shown. It is now two generations of 4096 lines each (a line used in the older
  one moves to the newer one; when the newer is full the older is dropped).
- Input method (commit 0563338): the Metal view is an NSTextInputClient. While a
  context says it takes text (=set-text-input-caret=), a key goes through
  =interpretKeyEvents:= and what comes back is a text event, a composition event
  (started, changed, committed, with the selection in characters) or, for a
  command such as an arrow, the key. =firstRectForCharacterRange:= answers from
  the caret the context holds. No C was needed: =define-alien-callable= returns
  NSRange and NSRect by value.

What the editor showed about the interfaces:
- A retained canvas that has not changed is not drawn again but kept as commands
  and drawn at an offset, so its painter runs at 0, 0 and not at its place in
  the window. =set-text-input-caret= takes window coordinates, which a painter
  in that variant does not have. All three editors ask =lookup-target= for the
  canvas's place (the answer is that of the last frame, and a canvas that is
  moved without being redrawn would give the input method an old place). The
  first version used the painter's x and y and passed in the immediate variant
  only.
- A canvas's event handlers are not given the text engine, so a click cannot be
  turned into a column by measuring. The painter stores the width of a character
  in the document, which works because the editor's font is of equal widths; a
  proportional font would need the engine (or the lines it laid out) in the
  handler.
- The document changes in place. A signal does not see that, so the reactive
  version has a count of changes as its one signal; the retained version
  invalidates the canvas by hand; the immediate version needs neither. This is
  the first model in the project that is not a value; an immutable document (a
  rope, or a persistent sequence) would let the reactive version hold it as its
  state, and is not tried.
- The three variants draw the same editor: their display lists differ in one
  command, the unused rectangle of an =unclip=, which the retained and reactive
  variants offset with the canvas and the immediate does not. The 394 checkpoint
  hashes of the editor session are the same in the retained and the reactive and
  all differ in the immediate; the rows script does the same. The dashboard's
  lists differ in four commands of two kinds, which was not looked into.

* Decision
Proposed: keep the three apps, their scripts and tests as the stress set, and
the bounded cache. H1 and H3 stay OPEN. The stress apps lean the way the small
ones did on code size (the immediate variant's file is smallest) and show no
difference in frame time through the host or in a window, nor, once the handling
of an event is counted with the frame, in the cost of an edit (on allocation,
the one app with no input shows the reactive variant at 27 K a frame and the
immediate at none); that is the shape H1 expects, from one machine, one author
and three apps. On H3, the input method needed the same two hooks on the canvas
and the same controller in the three variants; adding the hooks to the libraries
took 61, 16 and 44 lines in the retained, reactive and immediate (it routes text
to the focused node by generic functions in the retained), which is one datum
and not a verdict; what H3 says about accessibility and the machine interface is
for step 4.

Proposed, and for Micah to choose: (a) =set-text-input-caret= takes the caret in
the canvas's own coordinates and the variant adds the canvas's place, so that an
app does not have to ask where its canvas is; (b) an =unclip= keeps no rectangle
(=push-unclip= and =append-display-list= leave it zero), so that a display list
and its hash are the same across variants; (c) handlers are given the context,
or the canvas keeps the lines it laid out, if a proportional-font editor is
wanted; (d) the harness times and counts =handle-event= with the frame, for
every variant, so that the cost of an event is the same thing in each (the
records of the 7GUIs scripts and of 0021 and 0023 have the asymmetry described
above, and their tables of the build are of the frame only). None is done.

* Consequences
- Easier: three apps that stress the text cache, the scroll, the animation and
  the input method, run in the three variants with the same tests, scripts and
  metrics; the line cache cannot grow without bound.
- Open: a real input method (Japanese, Chinese or an accent menu) has to be
  tried by a person in a window; the tests send what an input method sends and
  cannot tell if the candidate window is where the caret is. The editor has no
  horizontal scroll (lines are at most 80 characters), no undo, no clipboard and
  no word or line selection by click. The non-arm64 Mac is for later: the
  Objective-C layer passes structures in registers in ways that are arm64's.
- Not done: the dashboard's lists differing across variants; an immutable
  document; H5 (node pooling) needs the variants changed and is not part of
  this.
