#+TITLE: 0020 — The layout spike (H6): what it showed
#+DATE: 2026-10-26
- Status :: proposed

* Context
H6 expects that an immediate-mode front end cannot reach complex layouts by
placing widgets as they are emitted, as Dear ImGui does, because a parent cannot
know its children's sizes until they are drawn. It would need a node tree built
each frame and laid out afterwards, or children that return a size and local
commands. The charter's spike asks for the same layouts in every front end (the
Flight Booker and Cells, a nested split panel, a wrapped paragraph in a
resizable container) and, for each, the layout lines of code, the time of the
layout, the builds per settled frame, and whether the display lists match across
front ends. The outcome is to be a record. 0010 chose, for all three variants,
the same layout functions over a tree that the variant owns, and the immediate
variant made its tree of boxes each frame (0016).

* What was built
The Flight Booker and Cells were already in all three variants. New: a paragraph
(text broken into lines to the width it is given, so that its height depends on
its width) in each variant, and the screen of =apps/7guis/layout=: a sidebar
beside a right side that is split down into a top and a bottom, the bottom split
across again, with a paragraph in each pane (the nested split is a row or column
whose children have flex factors). The window is made a width wider or narrower,
as a person resizing it does.

* Evidence
- Builds per settled frame: 1, in every variant, at every one of 311 widths from
  280 to
  900. Nothing was laid out a frame late and no extra build was needed.
- Display lists: at all 311 widths, with the real text engine, the three
  variants drew the same list bit for bit. With the fake text of the tests, the
  same at 16 widths.
- Time, with the real text engine and no window, a frame at a new width (layout
  and painting needed): retained 431 us, reactive 432 us, immediate 441 us; a
  frame at the same width: 1.7, 1.9 and 3.0 us. The cost is the text engine's,
  which breaks and measures the paragraphs, and is the same in all three. 8.7 to
  9.4 KB are consed in a frame at a new width, from the text engine's lists and
  the substrings of the lines.
- Lines of code for the paragraph: retained 86 (the node, its layout and its
  painting), reactive 16 more on the retained one (the view, and the
  reconciler's cases), immediate 87 (the widget and its state, the layout case,
  the drawing). The screen itself is 40, 41 and 41 lines of code.
- Planning the resizable window found two defects of the immediate variant that
  no test had met: it skipped layout and painting when the boxes it described
  were the same, without asking whether the window was (a resized window kept
  its old places), and a box's kept drawing did not know the size it was drawn
  at. Both are fixed, with tests that fail without the fixes.
- What was not tested: a cursor-style layout, which places widgets as they are
  emitted. No front end here does, so the cases that would need a lagged size or
  an extra build were not counted, only shown to be none for a front end that
  lays out after the description.

* Decision
The shared layout functions over a tree the variant owns, which for the
immediate variant is a tree of boxes made each frame and laid out after the
description, are enough for these layouts: a nested split and wrapped text in a
resizable window, with no lag, no extra build and the same display list as a
retained tree. The core does not need to own a box tree (0010, option 3 of its
first question stays unchosen), and the variants stay as they are. What H6
expected about a cursor layout is neither confirmed nor refuted by this: it is
untested, and the charter's position that cursor layout is not the reference
stands.

* Consequences
- Easier: one layout code for three variants; an immediate variant that is
  correct for any window size and any paragraph, at the price of the box tree.
- Harder: the immediate variant must remember that anything layout works out
  (the lines of a paragraph) has to live where a frame whose layout is skipped
  can still find it: it is in the state of the box's key.
- Open: H6 stays open for a cursor-style front end, if the experiment is wanted:
  a small immediate widget set that places as it emits, with the same screen, to
  count the lags.
