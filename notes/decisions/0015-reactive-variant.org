#+TITLE: 0015 — The reactive variant: views over signals, on retained nodes
#+DATE: 2026-10-26
- Status :: accepted (Micah, 2026-10-26)

* Context
The charter's reactive hybrid is told what changed (a notification or a dependency
tracker), describes again only the parts of the UI that depended on it, and compares what
it described with a persistent tree that has stable identity (Flutter's elements and render
objects, GPUI's views). The retained variant already has the persistent tree, with layout,
painting, caching and input. What is left to build is how a reactive app holds its state
and changes the tree.

* Options
1. A second, separate node library for the reactive variant.
2. The reactive variant builds on the retained nodes: it adds signals, view descriptions
   and a reconciler, and the retained nodes are its render objects.

* Evidence
- Flutter's widgets are descriptions that are cheap to make again; its elements are the
  persistent tree; its render objects do layout and painting. The retained nodes play the
  last two roles here, and a reconciler is the first.
- What the experiment compares is how an app is written and what it costs to change and
  run (H1, H2, H5). A second node library would repeat layout, painting, hit testing, focus
  and the paint cache, which are not what differs, and would put two copies of them in the
  comparison.
- The acceptance tests (0013) drive every variant through ids, pointer and key events and
  what is drawn, so they hold the reactive variant to the retained one's behaviour.

* Decision
Option 2. =variants/cl-reactive= has four files. =signals= has signals (a value that tells
those who read it when it changes, unless it is EQL to what it was), computed values (kept
until what they read changes) and observers. =views= has the descriptions an app returns:
a constructor for each widget, taking children first and options after, and
=component=, a part of the screen described by a function. =elements= is the reconciler: a
persistent element for each view, holding its retained node; describing again changes a
node that differs in place (a label's text, a field's value, a list's items), keeps the
others and what they hold, matches children by kind and =:key=, and makes a new node when a
property that a node is made with (a gap, a width) differs. =reactive= is the variant: a
frame runs tickers, then describes again the components that were told, outermost first,
and then the retained variant lays out and paints.
Inputs are controlled: what a view says is what they show. A person's typing goes to the
view's handler, and the component is described again, so that a change the handler refused
is undone. Two changes before a frame make one description. A component that keeps writing
what it reads is an error after 50 rounds.

* Consequences
- Easier: the reactive variant is small, its apps are functions of state, and it gets
  retained painting, hit testing and caching without a copy.
- Harder: its costs are the retained variant's plus describing, comparing and
  tracking, and any comparison of the variants' frame times has to separate them.
  Whatever the retained nodes cannot do, it cannot.
- Gives up: a render tree of its own, such as one that shares nodes between components.
