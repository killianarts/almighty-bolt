#+TITLE: 0013 — The 7GUIs apps: what is shared, and where they differ from the task
#+DATE: 2026-10-26
- Status :: accepted (Micah, 2026-10-26)

* Context
Phase 2 asks for all seven 7GUIs tasks in each of the three variants. The point of
building them three times is to compare the approaches, so what the approaches do not
differ in should be written once, and where a task cannot be done as written with the
core as it stands, the difference should be recorded and be the same in all three.

* Options
For what is shared:
1. Each variant's app has its own logic as well as its own UI.
2. The logic of a task (what a text means as a number, what a valid date is, how a timer
   runs, how a spreadsheet works out its cells, how a drawing is undone) is shared, as
   values and pure functions, and each variant writes the UI and holds the state its
   own way.

For the parts of the tasks the core cannot yet draw or do:
1. Add what is missing (clipping, a popup that floats, timers) to the core first.
2. Do the task another way that the core can do now, the same way in all three variants,
   and record the difference.

* Evidence
- 0009 puts what an event means with the variant. What a variant holds (nodes, signals,
  a table of states keyed by id) and when it builds is what H1 to H3 and H5 compare. A
  spreadsheet's formula parser is not any of those, and written three times it would be
  noise in the line counts the change-cost tests will take.
- The display list has rectangles, rounded rectangles and glyphs (0008), and no clip.
  A circle is a rounded rectangle whose radius is half its width. A scrolling list can
  be drawn with only the rows that are in view, and the text of a cell cut to the cell's
  width using the text engine's own measurement (=context-index-at-x=).
- A timer is an animation: 0009 says an animating variant asks for the next frame
  itself, and the core clock gives the time. No host timer is needed.

* Decision
Option 2 for the logic. It lives in =apps/7guis/<task>/model.lisp=, with the system
=almighty-bolt-7guis= and its own tests: =common/numbers= (what a text is as a number),
=temperature=, =flight= (dates as dd.mm.yyyy, with real calendar checks), =timer=,
=crud= (entries as values, with a filter by surname prefix), =circles= (a drawing with
undo and redo as values) and =cells= (26 columns, rows 0 to 99, formulas with
+ - * /, brackets, references, ranges, SUM, AVG, MIN, MAX and COUNT, with =#ERR= and
=#CYCLE=). Each variant has =apps/7guis/<task>/<variant>.lisp= for the UI.

Option 2 for what the core cannot do. The seven apps differ from the task's text in
these ways, the same in every variant:
- The flight booker's combo box is a choice between its two options shown side by side
  (a radio group), since a pop-up list that floats over other widgets needs painting
  after everything else, which none of the variants has yet.
- A list or a grid draws only what is in view and cuts text to the width of its cell. It
  does not clip, so a partly visible row is not drawn.
- The circle drawer's pop-up menu is left out: right-clicking a circle opens the diameter
  dialog straight away. The dialog is a panel drawn over the canvas that takes the pointer
  until it is closed.
- The timer updates at the display rate while it runs and not at all when it has
  stopped.
- Text fields have no clipboard and no input methods (0012).

A task is a window of a fixed size per task, opened with
=make 7guis VARIANT=retained TASK=counter=. =LOG=1= prints what keys and presses arrive.

* Consequences
- Easier: the three UIs of a task can be compared by what they hold and how they build,
  and the model tests cover the behaviour of the task once.
- Harder: a variant cannot change a task's rules; a change to a rule changes all three.
- Gives up: apps that look exactly like the 7GUIs reference, until the core has clipping
  and floating layers. A record to add them is for the review.
